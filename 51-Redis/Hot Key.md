## 热点key
热点Key是什么->危害->排查->解决方案->Big Key->面试高频题
### 热点Key是什么
Hot Key：被超高频率访问的key。当访问量超过单个redis节点的处理能力时，形成性能瓶颈。
```
// 例子：
// ① 爆款商品：product:100 被 100 万用户同时抢购
// ② 热搜词：top:keyword 每秒百万次访问
// ③ 秒杀库存：stock:sku:100 大量并发扣减
// ④ 排行榜：leaderboard 高频读取
```
热点key和普通key
```
// 普通 key：每秒几十/几百次访问，没问题
// 热点 key：每秒几十万/百万次访问
// 单个 Redis 单线程处理能力：约 10 万 QPS
// 超过 → 该 key 的请求排队 → 延迟暴涨 → 拖垮整个 Redis
```
### 危害
单点瓶颈
```
// 所有热点请求都打同一个 key
// Redis 单线程串行处理 → 排队
// 其他 key 的请求也被拖慢（排队）
```
打爆单节点
```
// 在 Cluster 中，热点 key 只在一个节点
// 其他节点空闲，这个节点被打满
// 数据倾斜 + 流量倾斜
```
级联故障
```
// Redis 被打满 → 请求超时 → 应用层重试
// 重试更多请求 → Redis 更堵 → 超时更多
// 雪崩：缓存层崩 → 请求打到数据库 → 数据库也崩！
```
### 怎么发现热点key
客户端统计
```
// 在应用层统计 key 访问次数
// 拦截 Redis 操作，计数
// 超过阈值 → 上报告警
// 缺点：侵入业务代码
```
redis-cli分析
```
# hotkeys 参数（需要开启 LFU）
redis-cli --hotkeys
# 输出访问频率最高的 key

# 需要配置：
# maxmemory-policy allkeys-lfu
```
monitor命令
```
# 监控所有命令（生产慎用，影响性能）
redis-cli monitor
# 观察高频出现的 key
```
代理层统计
```
// 使用代理（如 Codis、Proxy）时
// 代理统一统计 key 访问频率
// 无侵入
```
业务预判
```
// 运营活动前预判：
// 秒杀商品、热门直播、热点新闻
// 提前知道哪些 key 会热 → 提前处理
```
### 解决方案
#### 方案一：本地缓存
```
// 热点 key 在 JVM 本地缓存一份（Caffeine）
// 大量读请求直接命中本地 → 不访问 Redis

// 流程：
// ① 本地缓存（Caffeine）—— 快（纳秒级）
// ② 未命中 → 查 Redis
// ③ 未命中 → 查数据库回写

// 好处：
// ① 彻底解决 Redis 热点（流量分流到每个应用实例）
// ② 读性能最高（本地内存）

// 注意：
// ① 本地缓存一致性：需要失效机制
// ② 每个实例一份 → 数据短期不一致
// ③ 热点过期瞬间 → 本地也失效 → 需配合其他方案
```
#### 方案二：热点key备份
```
// 把热点 key 复制 N 份（加后缀），分散到不同"逻辑 key"

// 例：product:100 热点
// 拆成：
// product:100:0、product:100:1、product:100:2 ...（N 份）

// 写入：写 N 份（或只写主 + 异步同步）
// 读取：随机选一个副本读（分散流量）

// 好处：
// ① 流量分散到 N 个 key（Cluster 中分散到 N 个节点）
// ② 解决单节点瓶颈

// 注意：
// ① 写放大（N 份写入）
// ② 数据一致性（多副本）
// ③ 适合"读多写少"的热点

// Redis 4.0+ 有热 key 自动分裂方案，但一般手动/中间件做
```
#### 方案三：redis集群扩容+数据倾斜治理
```
// ① Cluster 扩容：增加节点
// ② 热点 key 用 hash tag 强制分散？不行（反而集中）
// ③ 合理设计 key：避免所有流量打一个槽

// 本质：热点是"单个 key"问题，扩容单节点帮不了
// 需要"热点分散"（方案二）或"本地缓存"（方案一）
```
#### 方案四：读写分离+从节点
```
// 热点 key 的读请求分发到从节点
// 主节点只承担写
// 但：从节点复制同一份热点 → 每个从节点也有热点
// 治标不治本（缓解不解决）
```
#### 方案五：限流\降级
```
// 超出处理能力时：
// ① 限流：拒绝部分请求（快速失败）
// ② 降级：返回兜底数据（本地快照/默认值）
// ③ 熔断：暂时停止访问 Redis

// 防止级联故障（Redis 崩 → DB 崩）
```

|方案|效果|复杂度|一致性|
|---|---|---|---|
|**本地缓存**|最好 ✅|中|弱（可接受）|
|**key 备份分散**|好|中|弱|
|**扩容**|一般|低|好|
|**读写分离**|缓解|低|中|
|**限流降级**|兜底|低|—|
### Big Key治理
```
// 单个 key 的 value 过大：
// ① 单个 String 值 > 10KB（或 100KB）
// ② 集合类型元素过多：List 百万元素、Hash 百万字段
// ③ 整个 key 的序列化大小 > 1MB（常见标准）
```
Big Key的危害
```
// ① 阻塞：删除/获取大 key 耗时（单线程阻塞所有请求）
//    DEL bigkey → 阻塞几秒 → 全 Redis 卡死！
// ② 内存不均：Cluster 中单节点内存倾斜
// ③ 网络压力：传输大 value 慢
// ④ 慢查询：读/写大 key 都慢
```
发现Big key
```
# 扫描大 key
redis-cli --bigkeys
# 输出最大的 key

# 或者用 SCAN 遍历分析（不阻塞）
```
处理Big Key
```
// ① 删除大 key：用 UNLINK（异步删除）替代 DEL
//    DEL bigkey    → 同步删除（阻塞）
//    UNLINK bigkey → 异步删除（不阻塞）✅

// ② 拆分大 key：
//    一个大 List → 拆成多个小 List
//    大 Hash → 按业务拆成多个 key

// ③ 压缩/优化存储：
//    大 JSON → 用 Hash 存字段
//    大文本 → 压缩后再存

// ④ 设置上限：
//    集合类型限制元素数量
//    String 限制长度
```
