## 缓存三大问题
三大问题总览->缓存穿透->缓存击穿->缓存雪崩->问题对比->面试高频题
### 三大问题总览
| 问题     | 场景          | 本质          |
| ------ | ----------- | ----------- |
| **穿透** | 查不存在的数据     | 缓存和库都没有     |
| **击穿** | 热点 key 过期瞬间 | 单个热点 key 失效 |
| **雪崩** | 大量 key 同时过期 | 大面积 key 失效  |
```
穿透：查了个"不存在的"（攻击/错误请求）
击穿：单个"热点"刚好过期
雪崩：一大片"同时"过期
```
### 缓存穿透
```
// 查询一个"缓存和数据库都不存在"的数据
// 缓存未命中 → 查库 → 也没数据 → 不写缓存 → 下次还查库
// 恶意请求/攻击：疯狂查询不存在的 id → 每次都打到数据库 → 数据库被打垮

// 例子：
GET user:-999
// 缓存没有 → 数据库也没有 → 不缓存
// 下一次再查 -999 → 还是查库 → 死循环打库
```
解决方式一：缓存空值
```
// 查不到数据时，也缓存一个"空值"（带短过期时间）

public User getUser(Long id) {
    // ① 查缓存
    String cached = redis.get("user:" + id);
    if (cached != null) {
        if ("NULL".equals(cached)) return null;  // 空值直接返回
        return parse(cached);
    }

    // ② 查库
    User user = userMapper.findById(id);

    if (user == null) {
        // ③ 缓存空值（短过期，如 5 分钟）
        redis.set("user:" + id, "NULL", 5, TimeUnit.MINUTES);
        return null;
    }

    // ④ 正常缓存
    redis.set("user:" + id, toJson(user), 30, TimeUnit.MINUTES);
    return user;
}

// 效果：不存在的 id 也走缓存，不打库
// 缺点：空值也占内存；过期后仍可能被打
```
解决方式二：布隆过滤器
```
// 请求先过布隆过滤器：
// ① 初始化：把所有存在的 id 加入布隆过滤器
// ② 请求：先查布隆过滤器
//    不存在 → 直接返回（一定不存在）✅ 不打库
//    存在 → 放行查缓存/库（可能有误判）

// 布隆过滤器特点：
// ① 判断"不存在"是 100% 准确的
// ② 判断"存在"可能有误判（哈希碰撞）

// 效果：恶意请求（随机 id）大部分被拦截
// 缺点：需要维护 id 集合；有误判率

// 实现：Redisson RBloomFilter、Google Guava BloomFilter
```
其他解决
```
// ③ 参数校验：
// id 必须为正整数、格式校验 → 非法请求直接拒绝
// ④ 限流：针对异常请求频率限制
// ⑤ 黑名单：发现攻击 IP 拉黑
```
### 缓存击穿
```
// 某个"热点 key"过期的一瞬间
// 大量请求同时到达 → 缓存未命中 → 全部打到数据库 → 数据库压力骤增

// 对比穿透：
// 穿透：查不存在的 key（一直打库）
// 击穿：热点 key 过期的瞬间（一次性冲击）

// 例子：
// 商品详情 key：product:100（热点，10 万 QPS）
// 过期了 → 10 万个请求同时查库 → 数据库被打垮
```
解决方式一：互斥锁
```
// 只有一个线程去查库重建缓存，其他线程等待

public Product getProduct(Long id) {
    // ① 查缓存
    Product product = getFromCache(id);
    if (product != null) return product;

    // ② 缓存未命中 → 尝试加锁（SETNX）
    String lockKey = "lock:product:" + id;
    boolean locked = redis.setIfAbsent(lockKey, "1", 3, TimeUnit.SECONDS);

    if (locked) {
        try {
            // ③ 拿到锁的线程查库 + 重建缓存
            // 注意：拿到锁后再次查缓存（防止其他线程已重建）
            product = getFromCache(id);
            if (product == null) {
                product = productMapper.findById(id);
                setToCache(id, product);
            }
            return product;
        } finally {
            redis.delete(lockKey);  // 释放锁
        }
    } else {
        // ④ 没拿到锁 → 等待后重试（或短暂 sleep 再查缓存）
        Thread.sleep(50);
        return getProduct(id);  // 递归重试
    }
}

// 效果：只有一个线程打库
// 缺点：加锁有阻塞；可能死锁（锁没释放，用过期时间兜底）
```
解决方式二：逻辑过期
```
// key 不设置真实过期时间，而是存"逻辑过期时间"

// 结构：value + 过期时间
// key: product:100 = {"data": {...}, "expire": 1700000000}

public Product getProduct(Long id) {
    // ① 查缓存
    String json = redis.get("product:" + id);

    ProductVO vo = parse(json);
    // ② 判断逻辑是否过期
    if (vo.getExpire() > System.currentTimeMillis()) {
        return vo.getData();  // 没过期，直接返回
    }

    // ③ 逻辑过期了 → 加锁重建（互斥）
    boolean locked = redis.setIfAbsent("lock:product:" + id, "1", 3, TimeUnit.SECONDS);
    if (locked) {
        try {
            // 查库重建，更新逻辑过期时间
            Product product = productMapper.findById(id);
            redis.set("product:" + id, toJson(product, now + 30min));
            return product;
        } finally {
            redis.delete("lock:product:" + id);
        }
    } else {
        // ④ 没拿到锁 → 返回旧数据（逻辑过期但可接受）
        return vo.getData();  // 返回过期的旧数据（兜底）
    }
}

// 效果：返回旧数据兜底，重建异步，用户体验不中断
// 缺点：数据短暂不一致（逻辑过期到重建完成）
```

|对比|互斥锁|逻辑过期|
|---|---|---|
|一致性|强（重建后一致）|弱（可能返回旧数据）|
|性能|有阻塞（等待）|无阻塞（返回旧值）|
|实现|简单|复杂|
|适合|一致性要求高|容忍短暂旧数据|
### 缓存雪崩
```
// 大量 key 在同一时间过期（或 Redis 宕机）
// 所有请求都打到数据库 → 数据库被压垮

// 对比击穿：
// 击穿：单个热点 key
// 雪崩：大面积 key

// 场景：
// ① 缓存设置了相同的过期时间（都 30 分钟）→ 同时过期
// ② Redis 宕机（所有缓存不可用）
```
解决方式一：过期时间随机化
```
// 给过期时间加随机值，避免同时过期

// ❌ 都设 30 分钟 → 同时过期
redis.set(key, value, 30, TimeUnit.MINUTES);

// ✅ 30 分钟 + 随机 0~5 分钟
int randomTime = 30 * 60 + new Random().nextInt(300);
redis.set(key, value, randomTime, TimeUnit.SECONDS);

// 效果：过期时间分散 → 不会同时失效
```
解决方式二：互斥锁/加锁排队
```
// 类似击穿的互斥锁
// 大面积失效时，只让一个线程查库重建
// 其他线程等待
```
解决方式三：多级缓存
```
// ① 本地缓存（JVM）：Caffeine
// ② Redis 缓存
// ③ 数据库

// Redis 挂了/大面积失效 → 本地缓存还能顶住
// 多一层保护
```
解决方式四：Redis高可用+降级
```
// ① 高可用：主从 + 哨兵/集群（Redis 不宕机）
// ② 服务降级：缓存不可用时，直接返回默认值/限流
// ③ 缓存预热：高峰前提前加载热点数据
```
完美解决方案
```
缓存雪崩的防线：
① 过期时间随机化（防同时过期）✅ 基础
② 互斥锁（防打爆数据库）
③ 多级缓存（本地缓存兜底）
④ Redis 高可用（主从/集群）
⑤ 服务降级（熔断、限流、返回默认值）
```
### 三大问题对比
| 对比       | 穿透      | 击穿       | 雪崩         |
| -------- | ------- | -------- | ---------- |
| **数据存在** | 不存在     | 存在（热点）   | 存在（大量）     |
| **范围**   | 单个/多个   | 单个 key   | 多个 key     |
| **触发**   | 查不存在    | 热点过期瞬间   | 同时过期/宕机    |
| **持续时间** | 持续（一直打） | 短（过期瞬间）  | 短（集中冲击）    |
| **核心方案** | 空值/布隆   | 互斥锁/逻辑过期 | 随机化/多级/高可用 |
```

② 击穿：单个热点 key 过期瞬间，大量请求同时打库

        Redis 高可用（主从/集群）、服务降级

核心：都靠互斥锁 + 缓存设计 + 高可用组合解决。"
```

### 面试高频题
#### 题目1：穿透，击穿，雪崩的区别
```
// 穿透：查不存在的（攻击）
// 击穿：单热点过期
// 雪崩：大面积过期/宕机
```
#### 题目2：布隆过滤器原理
```
// 位数组 + 多个哈希函数
// 不存在 100% 准确，存在可能误判
// 拦截不存在的请求
```
#### 题目3：缓存空值有什么问题
```
// ① 占内存（大量不存在的 key）
// ② 过期后仍可能被攻击
// ③ 需要短过期 + 定期清理
```
#### 题目4：互斥锁重建缓存的注意点
```
// ① 拿到锁后要再查一次缓存（防止重复重建）
// ② 锁要设过期时间（防死锁）
// ③ 释放锁要 finally（防止异常不释放）
```
#### 题目5：逻辑过期 vs 互斥锁
```
// 互斥锁：一致性强，有阻塞
// 逻辑过期：返回旧数据，无阻塞
```
#### 题目6：缓存预热是什么
```
// 启动时/高峰前，提前把热点数据加载到缓存
// 避免高峰时首次请求全部打库
// 实现：启动加载 / 定时任务 / 消息队列
```
