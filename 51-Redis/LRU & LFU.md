## 过期与淘汰
过期策略->惰性删除->定期删除->内存淘汰->八种淘汰策略->LRU vs LFU->面试高频题
### 过期策略
什么是过期
```
# 给 key 设置过期时间
SET user:1 "张三" EX 60        # 60 秒后过期
EXPIRE user:1 60               # 给已有 key 设置过期
TTL user:1                     # 查看剩余时间（-1 永久，-2 已过期）
```
过期后怎么办
```
// 问题：过期 key 什么时候被删除？
// 两种策略：
// ① 惰性删除：访问时发现过期 → 删除
// ② 定期删除：定时抽查删除

// Redis 两个都用（惰性 + 定期组合）
```
### 惰性删除
```
// 每次访问 key 时，先检查是否过期
// 过期了 → 删除，返回 nil
// 没过期 → 正常返回

GET user:1
// Redis 内部：检查 user:1 是否过期
// 过期 → 删除 → 返回 nil
```
优缺点
```
// 优点：
// ① 只删被访问的 key（CPU 开销小）
// ② 简单

// 缺点：
// ① 内存浪费：过期的 key 如果一直不被访问，一直占内存！
//    大量过期 key 没人访问 → 内存被占着不释放
// ② 需要配合定期删除解决
```
### 定期删除
```
// Redis 后台定时任务（默认 10 次/秒）：
// ① 从设置了过期时间的 key 中随机抽一批（默认 20 个）
// ② 检查并删除其中过期的
// ③ 如果删除比例 > 25%，再抽一批继续（循环）
// ④ 直到删除比例 <= 25% 或 耗时超过 25ms

// 参数：
// hz 10：后台任务频率（每秒执行次数）
```
为什么随机扫描而不是全部扫描
```
// 全部扫描：数据多时太慢（O(n)），阻塞主线程
// 随机抽查：每次只查 20 个，耗时可控

// 但随机 → 可能漏掉过期 key
// 所以必须配合"惰性删除"兜底
```
两种策略配合
```
过期 key 的处理：
    │
    ├── 被访问？ → 惰性删除（访问时删）
    │
    └── 没被访问？
        ├── 定期任务抽到 → 定期删除
        └── 一直没抽到 → 占用内存（靠内存淘汰兜底）
```
### 内存淘汰
```
// 内存有限（maxmemory）
// 数据写满 → 需要淘汰旧数据腾空间
// 注意：淘汰 ≠ 过期（淘汰是内存不够时主动删）
```
配置
```
maxmemory 1gb              # 内存上限（默认不限）
maxmemory-policy allkeys-lru   # 淘汰策略（默认 noeviction）
```
八种淘汰策略

|策略|范围|说明|
|---|---|---|
|**noeviction**|—|不淘汰，写操作报错（默认）|
|**allkeys-lru**|所有 key|淘汰最久没用的|
|**volatile-lru**|设了过期的|淘汰最久没用的|
|**allkeys-lfu**|所有 key|淘汰使用最少的|
|**volatile-lfu**|设了过期的|淘汰使用最少的|
|**allkeys-random**|所有 key|随机淘汰|
|**volatile-random**|设了过期的|随机淘汰|
|**volatile-ttl**|设了过期的|淘汰剩余时间最短的|
怎么选
```
// 生产推荐：allkeys-lru 或 allkeys-lfu

// ① allkeys-lru（默认推荐）：
// 淘汰最久未访问的
// 适合：缓存热点数据场景

// ② allkeys-lfu：
// 淘汰使用频率最低的
// 适合：访问频率差异大的场景
// （某些 key 访问很频繁但可能有一段时间不访问，
//  LRU 会误删，LFU 按频率更准）

// ③ volatile-* 系列：
// 只淘汰设置了过期时间的 key
// 适合：不确定哪些该保留时
```
### LRU vs LFU
Last Recently Used 
```
// 淘汰"最久没被访问"的
// 基于时间：多久没用了

// 问题：
// ① 数据访问是"突发性"的
//    某 key 昨天被大量访问，今天不用了 → LRU 可能还留着（错）
//    某 key 长期高频，但最近 1 小时没访问 → LRU 可能删了（错！）

// ② 近似 LRU（Redis 不维护精确链表）
//    Redis 的 LRU 是"近似"的：采样 N 个 key，淘汰最老的
//    参数 maxmemory-samples 5（采样数）
```
Last Frequently Used
```
// 淘汰"使用频率最低"的
// 基于频次：被用了多少次

// 优点：
// ① 抗突发访问
//    hot key 长期高频 → 即使最近没访问，LFU 也保留
// ② 更准确反映"真正的热点"

// 参数：
// lfu-log-factor：对数因子（防止无限增长）
// lfu-decay-time：衰减时间（访问频率随时间衰减）
```

|对比|LRU|LFU|
|---|---|---|
|**依据**|多久没用|用了多少次|
|**适合**|通用缓存|热点差异大的|
|**抗突发**|差|好|
|**实现**|近似采样|计数器+衰减|
|**生产默认推荐**|allkeys-lru|allkeys-lfu|
### 面试高频题
#### 题目1：Redis的过期删除策略
```
// 惰性删除 + 定期删除 组合
// 惰性：访问时检查删除
// 定期：后台随机抽查删除（10 次/秒）
```
#### 题目2：只靠惰性删除有什么问题
```
// 过期 key 不被访问 → 一直占内存
// 所以需要定期删除兜底
```
#### 题目3：内存淘汰有哪些策略
```
// 8 种：noeviction、allkeys-lru/lfu/random、volatile-* 等
// 生产推荐 allkeys-lru 或 allkeys-lfu
```
#### 题目4：LRU和LFU的区别
```
// LRU：多久没用（时间）
// LFU：用了几次（频率）
// LFU 抗突发访问，适合热点差异大的
```
#### 题目5：过期的key一定被删除吗
```
// 不一定！
// 惰性删除：不访问不删
// 定期删除：随机抽查，可能漏
// 所以过期的 key 可能暂时还在内存（浪费）
```
#### 题目6：大量过期key同时过期会怎么样
```
// 内存突然被大量释放？不会
// 但定期删除要处理大量过期 key → 主线程耗时（阻塞）
// 解决：设置过期时间加随机抖动（TTL + 随机值）
```
