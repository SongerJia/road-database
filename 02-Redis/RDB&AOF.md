## 持久化
为什么需要持久化->RDB->AOF->混合持久化->对比与选择->面试高频题
### 为什么需要持久化
Redis是内存数据库
```
// 数据在内存 → 进程退出/宕机 → 数据全丢！
// 所以需要持久化：把内存数据保存到磁盘

// 两个目的：
// ① 宕机恢复：重启后数据不丢
// ② 备份/迁移
```
三种持久化方式

|方式|全称|特点|
|---|---|---|
|**RDB**|Redis DataBase|快照，定时全量保存|
|**AOF**|Append Only File|追加日志，记录每条写命令|
|**混合**|RDB + AOF|4.0+，RDB 做底 + AOF 做增量|
### RDB
```
// 把某个时间点的内存数据"全量快照"保存到 dump.rdb
// 二进制格式（紧凑）
```
触发时机
```
# ① 自动触发（save 配置）
save 900 1        # 900 秒内至少 1 次写 → 保存
save 300 10       # 300 秒内至少 10 次写
save 60 10000     # 60 秒内至少 10000 次写

# ② 手动触发
SAVE      # 阻塞保存（直接写，期间阻塞所有命令）
BGSAVE    # 后台保存（fork 子进程，不阻塞）
```
BGSAVE原理（fork）
```
// BGSAVE：fork 一个子进程做快照
// ① 主进程 fork 子进程（复制页表，COW 写时复制）
// ② 子进程把数据写入临时 RDB 文件
// ③ 写完改名替换旧 RDB
// ④ 主进程继续服务（不阻塞）

// 写时复制（COW）：
// fork 后父子进程共享内存页
// 父进程要修改某页 → 先复制该页 → 修改副本
// 子进程读到的还是旧数据（快照一致性）

// fork 会短暂阻塞主进程（复制页表，数据量大时明显）
```
RDB的优缺点
```
// 优点：
// ① 文件紧凑（二进制），适合备份
// ② 恢复快（直接加载快照）
// ③ 子进程持久化，不影响主进程性能

// 缺点：
// ① 丢数据：两次快照之间的数据会丢！
//    save 60 10000 → 最多丢 60 秒数据
// ② fork 开销：数据量大时 fork 慢
// ③ BGSAVE 频繁时 IO 压力大
```
### AOF
```
// 记录每一条"写命令"，追加到 appendonly.aof
// 重启时重放命令恢复数据
// 以日志形式保存（文本格式）
```
开启与配置
```
appendonly yes              # 开启 AOF
appendfilename "appendonly.aof"
appendfsync everysec        # 刷盘策略（默认）
```
三种刷盘方式

|策略|行为|安全性|性能|
|---|---|---|---|
|**always**|每条命令都刷盘|最安全（最多丢 1 条）|最慢|
|**everysec**|每秒刷盘（默认）|丢 1 秒数据|中|
|**no**|交给操作系统|可能丢很多|最快|
AOF 重写
```
// 问题：AOF 无限追加 → 文件越来越大！
// 100 次 SET name x → 记录 100 条 → 只需要最后 1 条

// 解决：AOF 重写
// 用当前内存数据，生成最精简的命令集

// 触发：
// ① 手动：BGREWRITEAOF
// ② 自动：aof-rewrite-percentage（文件增长比）
//        aof-rewrite-min-size（最小大小）

// 重写流程（fork 子进程）：
// ① fork 子进程
// ② 子进程根据当前数据生成新 AOF
// ③ 期间的新写命令记录到缓冲区
// ④ 子进程完成后，把缓冲区的命令追加到新 AOF
// ⑤ 原子替换旧 AOF
```
AOF的优缺点
```
// 优点：
// ① 丢数据少（everysec 最多丢 1 秒）
// ② 可读性好（文本，能看懂命令）
// ③ 适合做数据恢复（精确到秒）

// 缺点：
// ① 文件比 RDB 大
// ② 恢复慢（重放所有命令）
// ③ 写性能有损耗（写日志）
```
### 混合持久化 （4.0）
```
// AOF 重写时，把 RDB 快照写入 AOF 文件头部
// 之后增量命令用 AOF 追加
// 兼具两者优点
```
结构
```
appendonly.aof（混合格式）：
┌────────────────────────┐
│  RDB 快照（二进制）       │  ← 基础数据（加载快）
├────────────────────────┤
│  AOF 增量命令（文本）     │  ← 快照后的新命令
└────────────────────────┘

// 开启：aof-use-rdb-preamble yes（默认）
```
恢复流程
```
// 重启加载：
// ① 读 AOF 文件头部的 RDB 部分（快速加载全量）
// ② 重放 RDB 之后的 AOF 命令（补齐增量）
// → 又快又不丢数据
```
为什么混合好
```
// 纯 RDB：加载快，但丢数据多
// 纯 AOF：不丢数据，但加载慢
// 混合：RDB 快照（加载快）+ AOF 增量（不丢数据）
```
### 对比与选择
| 对比       | RDB     | AOF    | 混合      |
| -------- | ------- | ------ | ------- |
| **文件大小** | 小       | 大      | 中       |
| **恢复速度** | 快       | 慢      | 快       |
| **丢数据**  | 多（间隔）   | 少（1 秒） | 少       |
| **可读性**  | 二进制     | 文本     | 混合      |
| **写性能**  | 好       | 略差     | 略差      |
| **占用内存** | fork 开销 | 低      | fork 开销 |
生产怎么选择
```
// 推荐：混合持久化（RDB + AOF 都开）
// ① RDB 开启：做备份/容灾
// ② AOF 开启：保证少丢数据
// ③ 混合格式：加载又快又安全

// 纯缓存场景（可丢）：
// 可以只开 RDB 或都不开

// 结论：
// 生产标准：AOF + RDB 混合开启

面试官："Redis 持久化方案？怎么选？"

"三种：
① RDB：定时全量快照（BGSAVE fork 子进程），文件小恢复快，但两次快照间丢数据
② AOF：记录每条写命令（appendfsync everysec），丢数据少但文件大恢复慢
③ 混合（4.0+）：AOF 重写时头部存 RDB 快照 + 增量 AOF，又快又不丢

生产推荐混合开启：RDB 做备份，AOF 保证少丢数据，
混合格式恢复时先加载 RDB 再重放增量。

关键参数：
appendfsync everysec（每秒刷盘，丢 1 秒数据可接受）
AOF 定期重写（BGREWRITEAOF）防文件无限增长。"
```
### 面试高频题
#### 题目1：RDB和AOF的区别
```
// RDB：全量快照，文件小恢复快，丢数据多
// AOF：追加命令，丢数据少，文件大恢复慢
```
#### 题目2：BGSAVE为什么阻塞小
```
// fork 子进程 + 写时复制（COW）
// 子进程读快照，主进程正常服务
// 只有 fork 瞬间和写复制有开销
```
#### 题目3：AOF重写是什么
```
// 用当前数据生成精简命令集，替换无限增长的 AOF
// 防止文件无限变大
```
#### 题目4：appendfsync三种策略
```
// always：每条刷盘（最安全最慢）
// everysec：每秒刷盘（推荐）
// no：交给系统（最快最不安全）
```
#### 题目5：混合持久化怎么恢复
```
// RDB 快照（快速加载全量）+ AOF 增量（补齐命令）
```
#### 题目6：持久化对性能有什么影响
```
// RDB：fork 有短暂阻塞，BGSAVE 有磁盘 IO
// AOF：每次写命令要追加日志（always 时最明显）
// 生产要监控持久化对主线程的影响
```
