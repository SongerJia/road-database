## 哨兵
哨兵是什么->三大功能->监控机制->主观/客观下线->故障转移流程->脑裂问题->面试高频题
### 哨兵是什么
Sentinel：Redis高可用的守护进程，监控主从节点的健康状态，主节点故障时自动进行故障转移。
为什么需要哨兵
```
// 只有主从的问题：
// 主节点挂了 → 没有自动切换 → 服务中断！
// 需要人工干预（手动提升从节点）

// 哨兵解决：
// ① 自动监控（发现主挂了）
// ② 自动故障转移（从节点变主）
// ③ 通知客户端（新主地址）
```
架构
```
┌──────────────┐
│   客户端      │
└──────┬───────┘
       │ 连接（获取主从地址）
       ▼
┌──────────────┐
│   哨兵集群     │ ← 3+ 个哨兵（高可用）
│ (Sentinel)   │
└──────┬───────┘
       │ 监控
       ▼
┌──────────────┐
│  主节点       │ ← 挂了 → 哨兵选从节点提升
│  从节点1 从节点2│
└──────────────┘
```
### 三大功能
Monitoring 监控
```
// 哨兵每秒向所有节点发送 PING
// 检查主从是否存活
// 检查主从复制是否正常
```
Notification 通知
```
// 节点状态变化时通知管理员/客户端
// 主节点切换时，通知客户端新主地址
// 客户端通过哨兵获取主节点地址
```
Automatic Failover 故障转移
```
// 主节点挂了：
// ① 从从节点中选一个提升为新主
// ② 其他从节点重新指向新主（replicaof 新主）
// ③ 客户端切换到新主
// 整个过程自动，无需人工
```
### 监控机制
心跳
```
// 哨兵每 1 秒向所有节点（主、从、其他哨兵）发 PING
// 参数：sentinel down-after-milliseconds 5000
// （5 秒没响应 → 判定为"主观下线"）
```
主从之间心跳
```
// 从节点每 1 秒向主节点发 REPLCONF ACK
// 报告自己的复制偏移量
// 哨兵通过这个检测从节点状态
```
### 主观下线 vs 客观下线
Subjectively Down   主观下行
```
// 单个哨兵认为节点挂了
// 条件：PING 超时（down-after-milliseconds）
// 只是"单个哨兵"的判断（可能误判！网络抖动）

// 哨兵 A 认为主挂了 → 主观下线（sdown）
// 但只有它一个这么认为 → 还不能切换
```
Objectively Down 客观下线
```
// 多个哨兵达成一致认为主挂了
// 条件：主观下线的哨兵数 >= 法定人数（quorum）

// 配置：sentinel monitor mymaster 127.0.0.1 6379 2
// 2 = quorum：至少 2 个哨兵主观下线 → 客观下线

// 只有客观下线才触发故障转移
// 防止单个哨兵误判
```
为什么需要quorum
```
// 单个哨兵可能误判（网络抖动、哨兵自己问题）
// 多个哨兵一致 → 更可靠
// quorum 建议：哨兵总数的一半 + 1（多数派）
// 哨兵 3 个 → quorum 2
// 哨兵 5 个 → quorum 3
```
### 故障转移流程
```
① 客观下线（多数哨兵认为主挂了）
    ↓
② 哨兵集群选出一个"领导者"（Raft 协议）
    ↓
③ 领导者从从节点中选出"新主"（评分）
    ↓
④ 通知其他从节点：replicaof 新主（重新指向）
    ↓
⑤ 旧主恢复后：replicaof 新主（变成从节点）
    ↓
⑥ 通知客户端新主地址（切换）
```
选举新主的评分规则
```
// 从节点按优先级筛选：
// ① 下线/断连的排除
// ② replica-priority 值小的优先（配置的优先级）
// ③ 复制偏移量大的优先（数据最新）
// ④ 运行 ID 小的优先（兜底）

// 选中的从节点 → SLAVEOF NO ONE → 成为新主
```
领导者选举（Raft）
```
// 故障转移前，哨兵集群要选一个"领导者"来执行
// 类似分布式共识：
// ① 每个哨兵投票给自己/他人
// ② 获得多数票的哨兵成为领导者
// ③ 领导者执行故障转移

// 保证：同一时刻只有一个哨兵执行切换（避免双主）
```
### 脑裂问题
```
// ① 主节点和客户端网络分区（主节点其实活着）
// ② 哨兵误判主挂了 → 提升新主
// ③ 旧主恢复连接 → 两个主 → 数据分裂！
```
缓解
```
# 主节点要求至少 1 个从节点确认才接收写
min-replicas-to-write 1
# 从节点延迟超过 10 秒视为不可用
min-replicas-max-lag 10

# 效果：
# 旧主失联（没有从节点同步）→ 拒绝写
# → 减少脑裂期间的数据写入
```
### 面试高频

> **Q:** "哨兵的作用？怎么实现高可用？" 
> **A:** "哨兵三大功能：监控（心跳）、通知、故障转移。主节点挂了：多个哨兵主观下线 → 达成 quorum 客观下线 → Raft 选出领导者 → 选从节点提升为新主 → 其他从节点重新指向 → 客户端切换。哨兵集群本身也要高可用（3 个以上），防止哨兵单点。"

> **Q:** "主观下线和客观下线？" 
> **A:** "主观下线：单个哨兵 PING 超时（可能误判）；客观下线：达到 quorum 的哨兵都认为下线（确认）。只有客观下线才触发故障转移。"
