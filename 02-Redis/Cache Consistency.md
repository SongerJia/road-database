## 缓存一致性
问题本质->更新策略->并发问题->落地实践->redis侧细节->面试高频题
### 问题本质
```
// Redis 和 MySQL 是两份数据
// 写操作要同时更新两个 → 顺序不一致 → 数据不一致

// 目标：不是强一致（做不到），而是"最终一致"
// 把不一致窗口尽量缩小
```
一致性的层级
```
// ① 强一致：任何时刻读到的都一样（几乎做不到，性能太差）
// ② 最终一致：一段时间后一致（业务可接受）✅
// ③ 弱一致：可能长期不一致（不可接受）
```
### 更新策略
| 策略                 | 写操作           | 一致性  | 适用     |
| ------------------ | ------------- | ---- | ------ |
| **Cache Aside**    | 更库 + 删缓存      | 最终一致 | ✅ 最常用  |
| Read/Write Through | 缓存代理库         | 中    | 框架场景   |
| Write Behind       | 只写缓存，异步写库     | 弱    | 容忍丢失   |
| **订阅 binlog**      | 只更库，Canal 删缓存 | 最终一致 | ✅ 生产可靠 |
推荐组合
```
// ① Cache Aside：先更新库 → 删除缓存（常规）
// ② 延迟双删：解决并发回写旧值
// ③ 过期时间兜底：即使删失败，过期后自然一致
// ④ 重试机制：删缓存失败 → MQ 重试
```
### 并发问题
问题：读回写旧值
```
// 场景：
// ① 线程 A：更新库（200）→ 删缓存
// ② 线程 B：读 → 缓存未命中 → 查库（旧值 100）
// ③ 线程 B：回写缓存 100（旧值！）
// ④ 线程 A：删缓存完成（但 B 在 A 删完后才写，可能写回）

// 不一致窗口：从 B 写回 100 到缓存过期
```
解决一：延迟双删
```
// ① 更新库
// ② 删缓存（第一次）
// ③ 延迟 500ms（> 读请求回写时间）
// ④ 再删缓存（第二次）

// 延迟时间怎么定？
// > 读请求"查库+回写缓存"的时间
// 一般 500ms~1s（看业务耗时）
// 可以测出读写耗时来定

// 注意：第二次删除要"保证成功"（MQ 重试）
```
解决二：消息队列保证删除
```
// ① 更新库成功
// ② 发"删缓存"消息到 MQ
// ③ 消费者删缓存
// ④ 删除失败 → MQ 重试（可靠投递）

// 优点：删除失败有重试兜底
```
解决三：Canal订阅binlog
```
// ① 应用只更新数据库（不管缓存）
// ② Canal 伪装成从库，监听 binlog
// ③ binlog 变化 → Canal 通知应用/直接删缓存
// ④ 幂等处理 + 重试

// 优点：
// ① 应用无侵入（不用手动删缓存）
// ② 可靠性高（binlog 有保障）
// ③ 和主从复制同一套机制

// 流程：
// 应用写库 → binlog → Canal → 删缓存/更新缓存
```
### Redis侧细节
删缓存vs更新缓存
```
// 为什么用"删除"不用"更新"？
// ① 更新要算新值（可能复杂，如聚合数据）
// ② 写多读少时，更新频繁浪费
// ③ 删除简单，读时懒加载
// ④ 避免并发更新冲突

// 例外：
// 计数器类（INCR）→ 更新更合适（Redis 自增原子）
// 简单值 → 更新/删除都行
```
删除失败的兜底
```
// ① 缓存过期时间（兜底）：即使删失败，过期后重建
// ② MQ 重试：删除失败消息重试
// ③ 重试表/定时任务：扫描未删成功的 key 补删
```
缓存过期时间设计
```
// ① 热点数据：相对短（30 分钟）→ 尽快一致
// ② 冷数据：相对长（24 小时）→ 省重建
// ③ 增加随机：防雪崩（呼应 R4）

// 原则：
// 过期时间 = 业务能容忍的最大不一致时间
// 一致性要求高 → 短过期（甚至不缓存）
```
