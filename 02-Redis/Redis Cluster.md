## 集群
为什么需要集群->分片原理->节点通信->请求路由->故障转移->和哨兵对比->面试题高频
### 为什么需要集群
单机/哨兵的限制
```
// ① 内存有限：单机内存有上限（64GB/128GB...）
// ② 写性能有限：单线程命令执行
// ③ 容量扩展难：升级机器（垂直扩展）有天花板
// ④ 哨兵只是高可用，不分片

// 数据量大到单机装不下 → 需要分片（水平扩展）
```
集群解决了什么
```
// ① 分片存储：数据分布到多个节点（水平扩展）
// ② 自动故障转移：节点挂了自动切换
// ③ 线性扩容：加节点即可扩容
// ④ 高可用 + 高容量

// 最少 3 主 3 从（生产推荐）
```
### 分片原理
```
// Redis Cluster 把数据空间分成 16384 个哈希槽（slot）
// 每个 key 通过 CRC16 哈希，对 16384 取模，落到某个槽

// 槽 = CRC16(key) % 16384

// 槽分配给节点：
// 3 个主节点：
// 节点1：槽 0~5460
// 节点2：槽 5461~10922
// 节点3：槽 10923~16383

// ① 心跳包传输槽位信息（bitmap 2KB，16384 位 = 2KB）
// ② 够用：最多 1000 个节点时每个节点也能分到 16 个槽
// ③ 太大 → 心跳包太大；太小 → 数据分布不均匀
// 16384 是性能权衡后的选择
```
数据分布示例
```
Cluster（3 主 3 从）：
┌─────────────┐ ┌─────────────┐ ┌─────────────┐
│  节点1（主）  │ │  节点2（主）  │ │  节点3（主）  │
│  槽 0~5460   │ │ 槽 5461~10922│ │ 槽10923~16383│
└─────────────┘ └─────────────┘ └─────────────┘
┌─────────────┐ ┌─────────────┐ ┌─────────────┐
│ 节点1副本（从）│ │ 节点2副本（从）│ │ 节点3副本（从）│
└─────────────┘ └─────────────┘ └─────────────┘

key = "user:123"
slot = CRC16("user:123") % 16384 = 5000 → 节点1
key = "stock:100"
slot = CRC16("stock:100") % 16384 = 9000 → 节点2
```
### 节点通信（Gossip）
集群内通信
```
// 节点间用 Gossip 协议通信（PING/PONG）
// ① 每个节点每秒和其他节点交换信息（心跳）
// ② 传播：节点的槽位信息、状态、故障信息
// ③ 通过 cluster meet 建立集群关系
```
Gossip特点
```
// ① 去中心化：没有中心节点
// ② 消息传播：节点之间互相传播状态
// ③ 最终一致：状态传播有延迟
// ④ 带宽可控：只交换摘要信息（槽位 bitmap）
```
### 请求路由
```
// 客户端可以连任意节点
// 数据可能在别的节点上

// ① 计算 key 的槽位
// ② 槽在哪个节点 → 找到节点
// ③ 连接那个节点操作
```
moved重定向
```
// 客户端连错节点时：
// 节点返回 MOVED 错误 + 正确节点地址

// 例：GET user:123 → 连接了节点2
// 节点2 计算：槽 5000 在节点1
// 返回：MOVED 5000 192.168.1.1:6379
// 客户端去节点1 操作
```
ASK重定向
```
// 槽位正在迁移时：
// 返回 ASK 错误
// 客户端去目标节点临时操作

// 区别：
// MOVED：槽已永久归属新节点（更新缓存）
// ASK：槽正在迁移（不更新缓存，一次性）
```
### 故障转移
节点状态
```
// 和哨兵类似：
// ① 主观下线（PFAIL）：单节点认为对方挂了（Gossip 超时）
// ② 客观下线（FAIL）：多数主节点认为挂了（超过半数）
```
故障转移流程
```
① 节点 A 被多数主节点判为客观下线（FAIL）
    ↓
② 从节点（A 的副本）发起选举（类似 Raft）
    ↓
③ 获得多数主节点投票的从节点胜出
    ↓
④ 从节点成为新主，接管 A 的槽位
    ↓
⑤ 其他节点更新槽位信息
    ↓
⑥ 客户端通过 MOVED 找到新主
```
与哨兵区别
```
// 哨兵：只做高可用，不存数据
// Cluster：既是分片存储，也自带故障转移
// Cluster 不需要哨兵（自己管自己）
```
### 集群 vs 哨兵
| 对比       | Sentinel | Cluster       |
| -------- | -------- | ------------- |
| **存储**   | 单机分片？不分片 | 分片（16384 槽）   |
| **容量**   | 单机上限     | 水平扩展 ✅        |
| **高可用**  | ✅        | ✅             |
| **故障转移** | 哨兵执行     | 集群自身          |
| **客户端**  | 连哨兵获取主地址 | 连任意节点 + MOVED |
| **节点数**  | 主从即可     | 最少 3 主 3 从    |
| **适用**   | 数据量不大    | 数据量大、高并发      |
怎么选？
```
// 数据量 < 单机内存（<64GB）：哨兵（简单）
// 数据量大/高并发：Cluster
// 一般生产：小规模哨兵，大规模 Cluster

// 注意：Cluster 有约束：
// ① 不支持多 key 操作（跨槽）：
//    MSET/事务/Lua 都要求 key 在同一槽
//    解决：hash tag（{user:1} 只对括号内取模）
// ② 数据库数量：只有 0 号库
// ③ 批量操作要自己算槽（pipeline 按槽分组）
```
### 面试高频题
#### 题目1：Cluster怎么分片
```
// 16384 个哈希槽
// 槽 = CRC16(key) % 16384
// 槽分配到节点
// 加节点 → 迁移部分槽
```
#### 题目2：Moved和ASK的区别
```
// MOVED：槽已永久移到新节点（客户端更新缓存）
// ASK：槽正在迁移（一次性操作）
```
#### 题目3：Cluster故障转移
```
// 多数主节点判 FAIL → 从节点选举（Raft）→ 新主接管槽位
```
#### 题目4：Cluster有什么限制
```
// 跨槽多 key 操作不支持（hash tag 解决）
// 只有 0 号库
// 批量操作要按槽分组
```
#### 题目5：为什么16384个槽
```
// 心跳包槽位 bitmap 大小权衡（2KB）
// 支持最多 1000 节点
```
#### 题目6：Cluster需要哨兵吗
```
// 不需要！Cluster 自带故障转移
// 哨兵是给单机主从用的
```
