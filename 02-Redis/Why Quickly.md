## Redis为什么快
四层原因->内存存储->单线程模型->IO多路复用->高效数据结构->面试高频题
### 四层原因
```
// Redis 快的原因（面试答题框架）：
// ① 基于内存存储（最快的原因）
// ② 单线程模型（避免锁竞争和上下文切换）
// ③ IO 多路复用（一个线程处理海量连接）
// ④ 高效的数据结构（SDS、跳表、压缩列表等）
```
性能数据
```
// Redis：10 万+ QPS（读），内存操作约 100ns 级
// MySQL：约 1000~5000 QPS（磁盘 IO）
// 相差 20~100 倍

// 为什么差这么多？
// 内存访问 ~100ns vs 磁盘随机 IO ~10ms
// 差 10 万倍（内存命中时）
```
### 基于内存存储（核心原因）
内存vs磁盘
```
// 内存访问延迟：~100 纳秒（ns）
// SSD 随机 IO：~100 微秒（μs）
// 机械盘随机 IO：~10 毫秒（ms）

// 内存比机械盘快约 10 万倍！

// Redis 数据全在内存：
// GET/SET 就是一次内存操作 → 极快
// MySQL 数据在磁盘（Buffer Pool 命中除外）
```
redis为什么敢用内存
```
// ① 数据量可控（缓存场景：只存热点）
// ② 内存价格下降（现在很便宜）
// ③ 持久化兜底（RDB/AOF 可恢复）
// ④ 淘汰策略（内存不足时淘汰旧数据）
```
### 面试高频

> **Q:** "Redis 为什么快？" 
> **A:** "主要是四点：① 内存存储（内存比磁盘快几个数量级）；② 单线程避免锁竞争和线程切换开销；③ IO 多路复用处理海量连接；④ 精心设计的数据结构（SDS、跳表、压缩列表）。核心是内存，其他是锦上添花。"
### 单线程模型
```
// 注意：Redis 的命令执行是单线程的（6.0 前完全单线程）
// 一个线程串行执行所有命令
// 同一时刻只有一个命令在执行
```
单线程的好处
```
// ① 无锁竞争：
// 多线程要加锁保证数据安全 → 锁竞争开销
// 单线程天然无竞争 → 不需要锁

// ② 无上下文切换：
// 线程切换有开销（保存/恢复状态）
// 单线程不切换 → 省开销

// ③ 实现简单、可维护性好
// ④ 单线程 + 原子性：单个命令天然原子（不用考虑并发）
//    所以 Redis 的 INCR 不需要锁就是原子的
```
单线程缺点
```
// ① 无法利用多核 CPU（一个核）
// ② 慢命令阻塞所有客户端（如 KEYS、大 key 删除）
// ③ 单点故障

// 解决：
// ① 多个 Redis 实例（分片）
// ② 避免慢命令（KEYS 用 SCAN 替代）
// ③ 6.0+ IO 多线程（只对网络读写，命令执行仍单线程）
```
Redis6.0的多线程
```
// Redis 6.0 引入 IO 多线程：
// ① 网络读写（解析/发送数据）多线程并行
// ② 命令执行仍然是单线程！
// ③ 因为网络 IO 占了大头，命令执行很快

// 默认关闭：
// io-threads 4（配置开启）
// 好处：高吞吐场景（大量连接）性能提升
```
###  IO多路复用
```
//传统IO问题
// 一个连接一个线程：
// 10000 个连接 → 10000 个线程 → 内存爆炸

// 阻塞等待：
// accept() 阻塞等连接
// read() 阻塞等数据
// 线程大部分时间在"等"，浪费

//IO多路复用
// 一个线程同时监听多个连接
// 谁有数据，处理谁（事件驱动）

// 核心系统调用：
// select / poll / epoll（Linux）

// 流程：
// ① 线程注册关注的连接（fd）到 epoll
// ② 线程阻塞在 epoll_wait
// ③ 某个连接有数据 → epoll 返回该连接
// ④ 线程处理有数据的连接
// ⑤ 继续阻塞等待下一个事件
```
单线程+多路复用模型
```
Redis 主线程（1 个）：
    │
    ▼
epoll（监听所有客户端连接）
    │
    ├── 客户端1 有数据 → 读取 → 执行命令 → 返回
    ├── 客户端2 有数据 → 读取 → 执行命令 → 返回
    └── 客户端3 有数据 → 读取 → 执行命令 → 返回
（串行处理，但都在内存，速度快）

// 10 万连接也只有一个线程
// 因为大多数连接"空闲"，真正有数据的少
// 多路复用让一个线程高效服务海量连接
```
和Nginx/Netty的关系
```
// 同样的模型：
// Redis、Nginx、Netty 都用 IO 多路复用
// 单线程/少量线程 + 事件驱动
// 这就是"高并发服务器"的标准模型
```
### 高效的数据结构
Redis的底层数据结构
```
// 5 种数据类型（String、List、Hash、Set、ZSet）
// 对应的底层实现：

// ① String → SDS（简单动态字符串）
//    比 C 字符串快（长度 O(1)、避免频繁扩容）

// ② List → 双向链表 / quicklist（压缩列表+链表）
//    头尾操作 O(1)

// ③ Hash → 哈希表 / 压缩列表
//    查找 O(1)

// ④ Set → 哈希表 / 整数集合
//    查找 O(1)

// ⑤ ZSet → 跳表（Skip List）+ 哈希表
//    有序查找 O(log n)

// 每种类型都针对场景优化过
```
为什么数据结构要优化
```
// ① 小数据用紧凑结构（压缩列表）→ 省内存
// ② 大数据用高效结构（跳表）→ 快
// ③ 根据元素数量和大小自动升级
// 例：哈希元素少时用压缩列表，多了升级为哈希表

// 这样 Redis 既省内存又快
```
### 高频面试题
#### 题目1：Redis单线程为什么这么快
```
// ① 内存操作本身就快（主要）
// ② 单线程避免锁和上下文切换
// ③ IO 多路复用（一个线程服务海量连接）
// ④ 数据结构高效
// 慢的是磁盘和网络，Redis 用内存 + 多路复用绕开了
```
#### 题目2：单线程会不会是瓶颈
```
// 会：慢命令（KEYS、大 key、批量写）会阻塞所有请求
// 解决：避免慢命令、SCAN 替代 KEYS、大 key 拆分
// 命令执行本身很快（内存操作），瓶颈在慢命令
```
#### 题目3：Redis6.0多线程怎么回事
```
// IO 多线程（网络读写并行），命令执行仍单线程
// 解决高连接数下的网络 IO 瓶颈
// 默认关闭，需要配置开启
```
#### 题目4：什么是IO多路复用
```
// 一个线程监听多个连接，谁有数据处理谁
// epoll 事件驱动
// Redis/Nginx/Netty 都这么干
```
#### 题目5：为什么单个命令是原子的
```
// 单线程执行命令 → 同一时刻只有一个命令在跑
// 天然原子（不需要锁）
// 所以 INCR 等命令并发下不会错乱
```
#### 题目6：redis快，mysql慢在哪
```
// Redis：内存操作 + 单线程 + 多路复用
// MySQL：磁盘 IO + 多线程锁竞争 + 解析优化执行
// 用途不同：Redis 缓存热点，MySQL 存全量数据
```
