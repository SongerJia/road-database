## 分库分表
为什么分库分表->垂直vs水平->分库分表策略->分片键与路由->带来的问题->中间件方案->面试高频题
### 为什么分库分表
单库单表的瓶颈
```
// 数据量增长 → 单表性能下降：
// ① 单表数据太大：索引变深、IO 变多
// ② 连接数有限：高并发撑不住
// ③ 磁盘/内存限制
// ④ 备份恢复慢

// 常见阈值：
// 单表 1000 万~2000 万行开始明显变慢（经验值）
// 实际看数据量 + 索引 + 硬件
```
演进路径
```
单库单表
  ↓ 数据量大
单库分表（水平拆表）
  ↓ 并发大
分库（垂直/水平拆库）
  ↓ 都大
分库分表（混合）
```
什么时候需要分
```
// ① 单表数据超过 1000 万+，查询明显变慢
// ② 优化索引、SQL、缓存后仍慢
// ③ 写入压力大，单库扛不住
// ④ 连接数不够

// 注意：分库分表是"最后手段"
// 先考虑：索引优化 → 缓存 → 读写分离 → 再分库分表
```
### 垂直 vs 水平
垂直分表（按字段分）
```
-- 用户表拆成：用户主表 + 用户扩展表
-- 主表：id, name, phone（常用字段）
-- 扩展表：id, address, avatar, bio（不常用字段）

-- 优点：大字段分离，减少行宽 → 单页存更多行
-- 缺点：查询需要 join（一般按 id 关联）
```
垂直分库（按业务分）
```
// 把不同业务拆到不同库：
// 用户库 user_db、订单库 order_db、商品库 product_db

// 优点：业务隔离、独立扩容
// 缺点：跨库无法 join、分布式事务
```
水平分表（按字段分）
```
-- 用户表按 user_id 拆成 4 张表：
-- user_0、user_1、user_2、user_3
-- 路由规则：user_id % 4 → 决定放哪张表

-- 优点：单表数据量减少
-- 缺点：跨表查询、全局排序复杂
```
水平分库
```
// 把同一张表的数据分布到多个库：
// order_db_0、order_db_1、order_db_2
// 路由：order_id % 3

// 优点：并发能力提升（多个库分担）
// 缺点：跨库查询、事务、全局 ID
```
对比总结

|方式|拆什么|解决什么|代价|
|---|---|---|---|
|垂直分表|字段|行宽、IO|join|
|垂直分库|业务|业务隔离、连接数|跨库 join|
|水平分表|行|单表数据量|跨表查询|
|水平分库|行到多库|并发能力|跨库事务|
### 分片策略
哈希取模
```
// 路由：shard = key % N

// 优点：数据均匀分布
// 缺点：扩缩容麻烦（N 变了，全部要迁移）

// 例子：user_id % 4
// user_id=1 → user_1
// user_id=2 → user_2
```
范围分片
```
// 路由：按时间/ID 范围分片
// user_2024、user_2025
// order_1~100万、order_100万~200万

// 优点：扩缩容简单（加新范围即可）
// 缺点：数据可能不均匀（热点集中在最新范围）

// 适合：日志、订单等有时间维度的
```
一致性哈希
```
// 解决取模的扩缩容问题
// 优点：扩缩容影响小（只迁移部分数据）
// 缺点：实现复杂

// 哈希环 + 虚拟节点
```
### 分片键与路由
分片键选择
```
// 分片键：决定数据分布到哪个分片

// 选择原则：
// ① 查询最频繁的条件（等值查询）
// ② 分布均匀（避免热点）
// ③ 不可变（改了要迁移）

// 例子：
// 订单表 → order_id 分片（按订单查）
// 用户表 → user_id 分片（按用户查）
// 但：按 user_id 查订单？→ 要路由到所有分片（广播）！
```
常见分片键问题
```
// 场景：订单表按 order_id 分片
// 业务：查"某个用户的所有订单" → WHERE user_id = 1
// 问题：order_id 分片，但查询条件是 user_id → 无法定位分片！
// 解决：全分片广播（扫描所有分片）→ 慢

// 更好的设计：
// ① 按 user_id 分片（按用户查订单快）
// ② 冗余表（订单分片 + 用户订单索引表）
// ③ 使用中间件（如 ShardingSphere 的绑定表）
```
### 分库分表带来的问题
跨库/跨表join
```
// 单库可以 join，分库后不行
// 解决：
// ① 冗余字段（把 join 的字段冗余到表里）
// ② 应用层组装（查完再拼）
// ③ 冗余表/宽表
// ④ 尽量用单分片查询
```
分布式事务
```
// 一个操作涉及多个分片 → 无法用本地事务
// 解决
// XA、TCC、Saga、Seata（AT 模式）
```
全局唯一ID
```
// 单库用自增 ID，分库后每个库自增会冲突！
// 解决：
// ① 雪花算法（Snowflake）✅ 常用
// ② 号段模式（美团 Leaf）
// ③ Redis 生成
// ④ UUID（不推荐，无序、太长）
```
分布式注解生成（雪花算法）
```
// 雪花算法 ID 组成（64 位）：
// ① 符号位：1 位（0）
// ② 时间戳：41 位（69 年）
// ③ 机器 ID：10 位（1024 台机器）
// ④ 序列号：12 位（每毫秒 4096 个）

// 特点：
// ① 全局唯一
// ② 趋势递增（时间戳在高位）
// ③ 高可用（本地生成，不依赖 DB）
```
分页与排序
```
// 问题：ORDER BY + LIMIT 跨分片
// 每个分片取前 N 条 → 应用层合并排序

// 问题：全局统计（COUNT、SUM）
// 每个分片统计 → 应用层合并

// 深分页更麻烦：
// 每个分片 LIMIT offset, size → 合并再取
// 数据量大会很慢 → 用游标/业务主键分页
```
数据迁移与扩容
```
// 取模分片扩容：所有数据要重新分布！
// 方案：
// ① 双写迁移（新旧库同时写，逐步切换）
// ② 停机迁移（维护窗口）
// ③ 一致性哈希（影响最小）
// ④ 迁移工具（ShardingSphere 有）

// 取模例子：
// 4 个分片扩到 8 个 → 每个原分片的数据拆一半到新分片
```
### 中间件方案
| 中间件                        | 类型     | 特点            |
| -------------------------- | ------ | ------------- |
| **ShardingSphere**（Apache） | 客户端/代理 | 功能全，Java 生态 ✅ |
| **MyCat**                  | 代理     | 老牌，SQL 路由     |
| **Vitess**                 | 代理     | 谷歌开源，K8s 友好   |
| **Atlas**                  | 代理     | 360 开源，简单     |
ShardingSphere的两种模式
```
// ① Sharding-JDBC（客户端模式）：
// 在 JDBC 层拦截 SQL，路由到对应数据源
// 优点：性能好（无代理网络开销）
// 缺点：每个应用都要集成

// ② Sharding-Proxy（代理模式）：
// 独立部署，像 MySQL 一样连接
// 优点：应用无感知
// 缺点：多一层代理，性能略差

// 配置示例（分库分表）：
// order_db_0.order_0、order_db_0.order_1
// order_db_1.order_0、order_db_1.order_1
// 路由：order_id % 2 分库，% 2 分表
```
