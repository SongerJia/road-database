## 主从复制
主从架构->复制原理->三种复制方式->全量/增量同步->主从延迟->读写分离->面试高频题
### 主从架构
```
// 一个主库（Master）+ 多个从库（Slave）
// 主库负责写，从库负责读（读写分离）
// 数据通过 binlog 同步到从库
```
架构图
```
客户端
    │
    ├── 写请求 → 主库 Master（读写 binlog）
    │               │
    │               │ binlog 同步
    │               ▼
    │        从库1（读） 从库2（读） 从库3（读）
    │
    └── 读请求 → 从库（负载均衡）
```
为什么需要主从
```
// ① 读写分离：读请求分摊到从库，减轻主库压力
// ② 高可用：主库挂了，从库提升为主
// ③ 数据备份：从库作为实时备份
// ④ 灾备：从库可以在异地
```
### 复制原理
三个线程
```
// ① 主库的 binlog dump 线程（Binlog Dump）
// ② 从库的 IO 线程（I/O Thread）
// ③ 从库的 SQL 线程（SQL Thread）
```
完整流程
```
主库（Master）                     从库（Slave）
    │                                 │
    │ ① 写 binlog                     │
    │                                 │
    │ ←────── ② IO 线程拉取 ────────   │
    │                                 │
    │                                 │ ③ 写入 relay log（中继日志）
    │                                 │
    │                                 │ ④ SQL 线程读取并执行
    │                                 │
    │                                 │ ⑤ 数据更新到从库
```
详细步骤
```
// ① 主库执行写操作 → 记录到 binlog
// ② 从库 IO 线程连接主库，请求 binlog
// ③ 主库 binlog dump 线程推送 binlog 给从库
// ④ 从库 IO 线程把 binlog 写入 relay log（中继日志）
// ⑤ 从库 SQL 线程读取 relay log，顺序执行
// ⑥ 从库数据更新完成
```
为什么有relay log
```
// ① IO 线程和 SQL 线程解耦（一个拉取，一个执行）
// ② 异步：IO 线程可以先拉取存储，SQL 线程慢慢执行
// ③ 容错：SQL 线程失败可以重来（relay log 还在）
```
复制模式

|模式|主库等待|一致性|性能|
|---|---|---|---|
|**异步复制**|不等待从库确认|弱（可能丢）|高|
|**半同步复制**|等至少一个从库确认|中|中|
|**组复制/全同步**|等所有从库确认|强|低|
```
// MySQL 默认异步复制：
// 主库提交后立即返回，不管从库
// 主库宕机 → 从库可能缺少最后的数据（丢数据）

// 半同步（rpl_semi_sync_master_enabled）：
// 主库要等至少一个从库收到 binlog 才返回，已经拉取到生成relay log
// 减少丢数据（至少一个从库有数据）

// 全同步（组复制 Group Replication）：
// 所有从库都确认才提交
// 强一致，但性能差
```
### 全量 vs 增量同步
全量同步（初始化/重连）
```
// 场景：从库刚建立、或从库落后太多（relay log 丢了）

// 流程：
// ① 主库生成一致性快照（FLUSH TABLES WITH READ LOCK）
// ② 记录当前 binlog 位置
// ③ 快照传输给从库（mysqldump / 物理备份）
// ④ 从库加载快照
// ⑤ 从快照时的 binlog 位置开始增量同步
```
增量同步（日常）
```
// 场景：从库正常运行时
// 流程：
// ① 从库记录已执行的 binlog 位置
// ② 定期/实时从主库拉取新的 binlog
// ③ 顺序执行
```
延迟问题
```
// 为什么从库会延迟？
// ① 从库只有一个 SQL 线程（串行执行）
// ② 主库是并发写，从库串行执行 → 排队
// ③ 大事务（长时间占用）
// ④ 从库硬件差

// 如何查看延迟？
SHOW SLAVE STATUS;
-- Seconds_Behind_Master：延迟秒数
```
解决延迟
```
// ① 并行复制（MySQL 5.7+ 默认开启）
//    多线程 SQL 应用
// ② 减少大事务（拆小）
// ③ 从库硬件升级
// ④ 合理读写分离（容忍轻微延迟）
```
### 读写分离
实现方式
```
// ① 应用层路由（常用）：
//    Spring 读写分离（AOP + 数据源切换）
//    MyCat、ShardingSphere 中间件

// ② 代理层：
//    Atlas、MaxScale、ProxySQL

// ③ 直连配置：
//    主库一个数据源，从库一个数据源
```
读写分离的问题
```
// ① 主从延迟 → 刚写完就读从库 → 读不到！
//    场景：注册完立即查用户信息
//    解决：
//    - 强制读主库（关键查询走主库）
//    - 延迟容忍（展示层允许旧数据）
//    - 等待机制（写后 sleep 一小会再读从库）

// ② 事务一致性：事务内必须走主库
//    场景：事务中先写后读
//    解决：事务绑定主库

// ③ 从库故障：读请求要能切换
//    解决：连接池健康检查、故障切换
```
### 面试高频

> **Q:** "读写分离有什么问题？" 
> **A:** "① 主从延迟：刚写完读从库可能读不到，关键查询强制走主库；② 事务一致性：事务内必须走主库；③ 从库故障切换。"

> **Q:** "主从延迟怎么解决？" 
> **A:** "① 并行复制减少延迟；② 大事务拆小；③ 关键读走主库；④ 容忍短期延迟的业务走从库；⑤ 硬件升级。"

// 从库的中继日志
