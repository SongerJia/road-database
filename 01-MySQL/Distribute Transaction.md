## 分布式事务
分布式事务是什么->CAP与BASE->XA两阶段->TCC->Saga->Seata AT模式->方案选择->面试高频题
### 分布式事务是什么
分布式事务：跨多个数据库/服务的事务，保证多个节点上的数据操作要么全部成功，要么全部回滚。
```
// 场景：下单 + 扣库存 + 扣余额
// 订单库：插入订单
// 库存服务：扣库存
// 账户服务：扣余额
// 三个操作跨三个服务/数据库 → 需要分布式事务
```
难点是什么
```
// 本地事务：一个数据库，有 redo/undo/锁，容易保证
// 分布式事务：
// ① 没有全局锁（无法锁所有库）
// ② 没有全局日志（无法统一回滚）
// ③ 网络不可靠（调用可能超时）
// ④ 无法预知所有步骤（分步执行）
```
### CAP与BASE
CAP定理
```
// 分布式系统无法同时满足：
// ① C（Consistency）：一致性 —— 所有节点数据一致
// ② A（Availability）：可用性 —— 请求总能有响应
// ③ P（Partition tolerance）：分区容错性 —— 网络分区时还能工作

// 只能三选二：
// CA：放弃分区容错（单机，不适用分布式）
// CP：放弃可用性（强一致，如 ZooKeeper、etcd）
// AP：放弃一致性（最终一致，如大多数微服务）

// 网络分区不可避免 → 实际是在 C 和 A 之间权衡
```
BASE理论
```
// 最终一致性（AP 的实践）：
// ① BA（Basically Available）：基本可用
//    系统出现故障时，允许部分功能不可用
// ② S（Soft State）：软状态
//    数据可以处于中间状态（不一致）
// ③ E（Eventually Consistent）：最终一致
//    经过一段时间，数据最终一致

// 分布式事务的核心：保证最终一致性
// 而不是"强一致"（那样只能牺牲可用性）
```
### XA两阶段提交（2PC）
```
// XA：基于数据库的分布式事务协议
// 两阶段：Prepare（准备）→ Commit/Rollback（提交/回滚）
// 需要一个协调者（TM）+ 多个资源管理器（RM）
```
两阶段流程
```
协调者（TM）             参与者1（RM1）          参与者2（RM2）
    │                        │                      │
    │── ① prepare ───────→ │                      │
    │── ① prepare ───────────────────→ │
    │                        │── ① 锁定资源，返回OK ──│
    │←──── ① 全部 OK ─────────│                      │
    │                        │                      │
    │── ② commit ─────────→ │                      │
    │── ② commit ───────────────────→ │
    │                        │                      │
    │←──── ② 全部完成 ────────│                      │
```
两阶段提交的问题
```
// ① 同步阻塞：prepare 后资源被锁定，其他事务阻塞
// ② 单点故障：协调者挂了，参与者一直等待
// ③ 数据不一致：commit 阶段协调者挂了，部分提交部分没提交
// ④ 性能差：多次网络交互 + 锁持有

// 结论：XA 性能差，一般不用在互联网业务
// 适用于：银行、传统企业系统（小规模）
```
### TCC（补偿事务）
```
// TCC（Try-Confirm-Cancel）：
// 把业务拆成三个操作：
// ① Try：预留资源（检查 + 冻结）
// ② Confirm：确认执行（真正扣减）
// ③ Cancel：取消（释放预留资源）

// 应用层实现，不依赖数据库锁
```
示例：转账
```
// Try：检查余额充足 + 冻结转账金额
// Confirm：扣减转出账户余额，增加转入账户余额
// Cancel：解冻资金（如果任一参与者失败）

// 转账 A→B 100 元：
// ① Try：A 冻结 100 元，B 检查可收款
// ② 全部 Try 成功 → Confirm：A 扣 100，B 加 100
// ③ 任一 Try 失败 → Cancel：A 解冻 100
```
TCC的优缺点
```
// 优点：
// ① 不锁定资源（Try 冻结，不是锁整行）
// ② 灵活（业务可控制补偿逻辑）
// ③ 性能比 2PC 好

// 缺点：
// ① 侵入性强（每个操作都要写 Try/Confirm/Cancel）
// ② 实现复杂（要考虑幂等、悬挂、空回滚）
// ③ 代码量大

// 适合：需要强一致性、跨服务的核心链路
// 典型实现：Seata TCC 模式
```
### Saga（长事务/事务编排）
```
// Saga：把长事务拆成多个子事务（本地事务）
// 每个子事务有对应的补偿操作
// 任一子事务失败 → 逆向执行补偿操作

// 不像 2PC/TCC 需要全局锁和协调
// 用本地事务 + 补偿保证最终一致
```
两种实现方式
```
// ① 编排（Orchestration）：一个协调者定义流程
// 订单 Saga 流程：
// ① 创建订单（本地事务）
// ② 扣库存（本地事务）
// ③ 扣余额（本地事务）
// ④ 任一失败 → 逆向补偿：退余额 → 加库存 → 取消订单

// ② 编排（Choreography）：事件驱动，每个服务自己决定
// 订单创建 → 发事件 → 库存服务监听扣库存 → 发事件 → ...
// 缺点：流程分散，不好维护
```
示例
```
// 订单 Saga（补偿流程）：
// 成功路径：
// 创建订单 → 扣库存 → 扣余额 → 通知成功

// 失败路径（比如扣余额失败）：
// 扣余额失败
// → 补偿：加回库存
// → 补偿：取消订单
// → 结束（订单状态=失败）
```
Saga的优缺点
```
// 优点：
// ① 不锁资源（本地事务）
// ② 适合长事务（多个业务步骤）
// ③ 吞吐量高

// 缺点：
// ① 无隔离性（中间状态可见）
// ② 补偿逻辑复杂（要覆盖所有失败场景）
// ③ 最终一致性（不是实时一致）

// 适合：业务流程长、容忍最终一致的场景
// 典型实现：Seata Saga、DTM
```
### Seata AT模式
```
// Seata（阿里开源）：分布式事务中间件
// AT 模式：自动补偿模式（最常用）
// 基于"全局事务 ID" + 代理数据源 + 回滚日志
```
AT模式原理
```
// 三个组件：
// ① TC（Transaction Coordinator）：事务协调者
// ② TM（Transaction Manager）：事务管理器（发起方）
// ③ RM（Resource Manager）：资源管理器（参与者）

// 流程：
// ① TM 开启全局事务 → 拿到 XID
// ② 各服务执行本地 SQL（RM 代理数据源，记录 undo_log）
// ③ TM 提交/回滚全局事务
// ④ 需要回滚时：TC 通知各 RM，根据 undo_log 逆向补偿
```
AT模式的侵入性
```
// 对业务代码侵入小：
// 只需要 @GlobalTransactional 注解
// 不用写 Try/Confirm/Cancel（对比 TCC）

// 示例：
@GlobalTransactional  // 开启分布式事务
public void createOrder(Order order) {
    orderService.insert(order);      // 本地 SQL
    stockService.deduct(order);      // 跨服务调用
    accountService.deduct(order);    // 跨服务调用
}
// 任一失败 → 自动根据 undo_log 回滚所有

执行流程
order-service
  @GlobalTransactional
    ↓ 向 TC 申请 XID=123
    ↓ RootContext=XID:123

  orderMapper.insert()
    ↓ 注册分支1（order_db）

  storageClient.deduct()
    ↓ Feign Header: TX_XID=123
----------------------------------------
storage-service
  Filter: RootContext.bind("123")
  storageMapper.deduct()
    ↓ 注册分支2（storage_db）

异常发生
  order-service 抛异常
    ↓ 向 TC 发 rollback
TC
  ↓ 通知 order-service 回滚
  ↓ 通知 storage-service 回滚
各自用 undo_log 补偿
```
为什么加了注解没有用
1. **XID 没传过去**
    - 用了自定义 HTTP 客户端
    - 用了线程池 / CompletableFuture
    - 用了消息队列但没手动传 XID
2. **下游没接 Seata**
    - 没引入 seata 依赖
    - 没配 `tx-service-group`
    - 数据源没被 `DataSourceProxy` 代理
3. **下游又加了 `@GlobalTransactional`**
    - 会开启新全局事务，而不是加入原事务
4. **远程调用失败但没抛异常**
    - 返回 `Result.fail()` 但方法正常返回
    - Seata 以为成功了

|对比|Seata AT|TCC|
|---|---|---|
|**侵入性**|低（注解）|高（三个方法）|
|**原理**|undo_log 自动回滚|业务补偿|
|**实现**|代理数据源|手写|
|**性能**|中|高|
|**适用**|普通业务|高并发核心链路|
### 方案选择
```
// 强一致 + 规模小 → XA（2PC）
// 核心链路 + 高并发 → TCC（Seata TCC）
// 长流程 + 最终一致 → Saga（Seata Saga / DTM）
// 普通业务 + 快速落地 → Seata AT（最常用）

需要分布式事务？
    ├── 能接受最终一致？
    │   ├── 是 → Saga 或 AT
    │   └── 否 → 强一致
    │       ├── 规模小 → XA
    │       └── 核心高并发 → TCC
    │
    └── 不一定需要？
        ├── 能改造成"本地事务+MQ 最终一致"？
        └── 尽量减少分布式事务（拆服务/冗余设计）
```
### 面试高频

> **Q:** "分布式事务有哪些方案？怎么选？" 
> **A:** "① XA/2PC：数据库强一致，性能差；② TCC：应用层补偿，侵入高，适合核心链路；③ Saga：长事务+补偿，最终一致；④ Seata AT：注解式自动回滚，最常用。选择：能接受最终一致用 AT/Saga，强一致小规模用 XA，核心高并发用 TCC。另外能避免就避免（MQ 最终一致）。"

#### 题目1：什么是分布式事务？为什么难

```
// 跨服务/库的事务
// 难：无全局锁、无全局日志、网络不可靠
```
#### 题目2：CAP和BASE
```
// CAP：一致/可用/分区容错三选二
// BASE：基本可用 + 软状态 + 最终一致
// 分布式事务保证最终一致
```
#### 题目3：XA两阶段提交流程
```
// Prepare → Commit/Rollback
// 问题：阻塞、单点、不一致、性能差
```
#### 题目4：TCC是什么
```
// Try（预留）→ Confirm（确认）→ Cancel（取消）
// 应用层补偿，不锁资源，侵入高
```
#### 题目5：Saga是什么
```
// 长事务拆子事务 + 补偿
// 本地事务 + 事件/编排
// 最终一致
```
#### 题目6：Seata AT模式
```
// @GlobalTransactional + undo_log 自动回滚
// 侵入小，最常用
```
#### 题目7：怎么避免分布式事务
```
// ① 拆分合理：避免跨库操作
// ② 冗余设计：减少 join
// ③ MQ 最终一致：本地事务 + 消息
// ④ 事务消息（RocketMQ）
```
