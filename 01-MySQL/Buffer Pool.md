## Buffer Pool 和InnoDB特性
BufferPool是什么->为什么快->LRU淘汰->脏页刷新->Change Buffer->Double Write->自适应哈希->面试高频题
### Buffer Pool是什么
Buffer Pool(缓冲池)：InnoDB在内存中对的缓存区域，缓存数据页和索引页，减少磁盘IO。
```
// 磁盘 IO 是最大的瓶颈（比内存慢 10 万倍）
// 数据全在内存里 → 快

// 读：先从 Buffer Pool 找，找不到才读磁盘
// 写：先改 Buffer Pool（脏页），异步刷盘
```
内存布局
```
Buffer Pool（默认 128MB）：
┌─────────────────────────────────────┐
│  数据页缓存（数据行）                  │
│  索引页缓存（B+ 树节点）               │
│  undo 页                             │
│  锁信息（自适应哈希索引）               │
│  Change Buffer（插入缓冲）            │
└─────────────────────────────────────┘

参数：
- innodb_buffer_pool_size：缓冲池大小（关键参数！）
- 建议：物理内存的 50%~70%
- 数据库性能主要看它
```
### 为什么快
读流程
```
// ① 查 Buffer Pool（内存）→ 命中直接返回 ✅
// ② 未命中 → 读磁盘 → 加载到 Buffer Pool → 返回

// 命中率高 → 大部分操作在内存 → 快
```
写流程
```
// ① 修改 Buffer Pool 中的数据页（内存）→ 变脏页
// ② 写 redo log（顺序写，快）
// ③ 返回成功
// ④ 后台线程把脏页刷到磁盘（异步）

// 核心：写操作先改内存，日志保证不丢，磁盘异步刷
```
### LRU淘汰机制
为什么需要淘汰
```
// Buffer Pool 大小有限（默认 128MB）
// 数据比内存多 → 需要淘汰旧页，腾空间给新页
// 用 LRU（最近最少使用）算法
```
标准LRU问题
```
// ① 全表扫描污染：
// 一次 SELECT * 全表扫描，把大量冷数据页加载进来
// 把真正的热点数据挤出 Buffer Pool → 缓存失效

// ② 无法区分"真正热点"和"一次性数据"
```
InnoDB的LRU改进（分代LRU）
```
Buffer Pool 的 LRU 链表（分两段）：

┌────────────────────┬──────────────────────┐
│    年轻区（5/8）     │      老年代（3/8）      │
│  被访问过至少 2 次    │  新加载的页（只读 1 次） │
│  热门数据           │  全表扫描的数据          │
└────────────────────┴──────────────────────┘
  head（最近使用）      tail（最久未使用）

规则：
① 新页加载 → 放入老年代头部（不直接进年轻区）
② 老年代的页被访问 → 升级到年轻区头部
③ 只被读一次的数据（全表扫描）→ 留在老年代，很快被淘汰
④ 年轻区尾 → 回到老年代（降级）
⑤ 淘汰：只淘汰老年代尾部（最冷）
```
为什么分代能防污染
```
// 全表扫描的页：加载进老年代，读一次
// 如果不再访问 → 留在老年代 → 很快被淘汰
// 不会挤掉年轻区里的热点数据

// 而热点数据：被访问 → 升级到年轻区 → 长期保留
```
相关参数
```
// innodb_old_blocks_pct=37：老年代占 37%（默认 5/8 年轻区）
// innodb_old_blocks_time=1000：页进入老年代后至少等 1 秒才能升级
//   防止"一进来马上被访问"误判为热点
```
### 脏页刷新
什么是脏页
```
// 脏页：Buffer Pool 中被修改过、还没写回磁盘的数据页

// 干净页：和磁盘一致的数据页
```
刷新时机
```
// ① redo log 写满：必须刷（不刷无法覆盖日志）
// ② Buffer Pool 空间不足：LRU 淘汰脏页时刷
// ③ 系统空闲：后台线程主动刷
// ④ MySQL 关闭时：全部刷
```
刷新对性能影响
```
// 刷脏页会占用磁盘 IO
// 如果刷得慢 → redo log 写满 → 阻塞写操作（要等刷完）

// 参数：
// innodb_io_capacity：刷脏页的 IO 能力（机械盘 200，SSD 2000）
// 调大 → 刷得快，但占用更多磁盘 IO
// 调小 → 刷得慢，可能阻塞
```
### Change Buffer 插入缓冲
解决什么问题
```
// 二级索引（非唯一）的插入/更新很慢！
// 因为：二级索引数据是"无序"的（随机位置插入）
// → 修改二级索引页 → 随机 IO（慢）

// Change Buffer：把二级索引的修改"缓存"起来
// 等页被读入时，再合并写入
```
流程
```
// ① 修改二级索引页 → 页不在 Buffer Pool
// ② 不直接读磁盘，而是记录到 Change Buffer（内存）
// ③ 后台/读请求触发时，把 Change Buffer 合并到索引页

// 效果：把"随机写"变成"内存记录 + 顺序合并"
// → 减少随机 IO，写入更快

写二级索引（页不在 BP）
   ↓
写 change buffer（内存 + redo log）
   ↓
【还没 merge，所以二级索引页在磁盘上还是旧的】

可能触发 merge：
1. 用户读这个二级索引页 
2. 后台线程空闲合并  
3. 慢关闭  也是后台线程将二级索引页读到bufferPool
4. 崩溃恢复  也是后台线程将二级索引页读到bufferPool

merge 后：
二级索引页进入 Buffer Pool → 变成脏页
   ↓
page cleaner 把脏页 flush 到 .ibd
```
适用场景
```
// ✅ 适合：写多读少、二级索引多的表
// 例：日志表、订单表（插入频繁）

// ❌ 不适合：读多写少
// 读请求会频繁触发合并 → 反而增加开销

// 参数：
// innodb_change_buffer_max_size=25：Change Buffer 占 Buffer Pool 比例
// 0 = 禁用
```
### 面试高频

> **Q:** "Change Buffer 是什么？" 
> **A:** "InnoDB 的插入缓冲：二级索引的修改不直接写磁盘（随机 IO 慢），先缓存在 Change Buffer，等页面被读取时再合并写入。把随机写变成顺序写，提升写性能。适合写多读少、二级索引多的场景。"
### Double Write (双写)
```
// 页撕裂（Partial Page Write）：
// 写一个 16KB 数据页，系统崩溃时只写了 8KB
// → 页损坏（一半旧一半新）
// → redo log 恢复需要"完整的页"，但页坏了 → 无法恢复！
```
解决流程
```
// ① 把完整的页先写入 doublewrite buffer（内存）
// ② 从 buffer 顺序写入 doublewrite 文件（磁盘，连续两块 1MB）
// ③ 再把页写入实际位置（随机写）

// 崩溃恢复：
// ① 发现数据页损坏
// ② 从 doublewrite 文件恢复完整页
// ③ 再用 redo log 重放

// 参数：innodb_doublewrite=ON（默认）
```
### 面试高频

> **Q:** "Double Write 是什么？为什么需要？" 
> **A:** "双写缓冲：写页前先把完整页写到 doublewrite 文件，防止页撕裂导致崩溃后无法恢复。先顺序写 doublewrite，再随机写实际位置。代价是每次写多一次 IO（增加 fsync）。"
### AHI 自适应哈希索引
```
// Adaptive Hash Index：InnoDB 自动为热点页建立哈希索引
// 把 B+ 树的 O(log n) 查找优化为 O(1)

// 条件：
// ① 页被访问次数达到阈值（热点）
// ② 由 InnoDB 自动维护，无法手动创建
// ③ 只对等值查询有效（哈希只能等值）
```
注意事项
```
// ① 内存占用（默认占 Buffer Pool 的 1/64）
// ② 无法控制哪些页建立
// ③ 对范围查询无帮助
// ④ 参数：innodb_adaptive_hash_index=ON（默认）
```
