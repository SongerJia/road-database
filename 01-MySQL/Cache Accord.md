## 缓存一致性
为什么需要缓存->缓存读流程->四种更新策略->先删除缓存vs先更库->延迟双删->最终一致性方案->面试高频题
### 为什么需要缓存
```
// ① 数据库读压力大（热点数据反复查库）
// ② 高并发下数据库扛不住
// ③ 数据变化不频繁，读多写少

// 引入 Redis：
// ① 热点数据放缓存，读走 Redis（快）
// ② 减少数据库压力
// ③ 抗住突发流量（秒杀等）
```
缓存读流程
```
读请求
    │
    ├── ① 查 Redis
    │   ├── 命中 → 直接返回 ✅
    │   └── 未命中 ↓
    │
    ├── ② 查数据库
    │
    ├── ③ 回写 Redis（设置过期时间）
    │
    └── ④ 返回数据
```
核心矛盾
```
// 缓存和数据库是两份数据
// 写操作要同时更新两个地方 → 顺序不一致 → 数据不一致！
// 目标：尽量让不一致窗口最小（最终一致）
```
### 四种更新策略
Cache Aside 旁路缓存
```
// 读：先查缓存 → 未命中查库 → 回写缓存
// 写：先更新数据库 → 再删除缓存

// 为什么写操作"删除缓存"而不是"更新缓存"？
// ① 更新缓存可能频繁（写多次读一次）
// ② 更新缓存涉及复杂计算（不如删了，懒加载）
// ③ 删除更简单，避免并发更新冲突
```
Read/Write Through 读写穿透
```
// 缓存作为"主存储"的代理
// 应用只和缓存打交道
// 缓存自己负责和数据库同步

// 实现复杂，一般用现成框架（如 Memcached 模式）
```
Write Behind 异步写回
```
// 写操作只更新缓存，异步批量写回数据库
// 好处：写性能极高
// 风险：宕机丢数据
// 适合：可以容忍丢失的场景
```

|策略|一致性|性能|复杂度|适用|
|---|---|---|---|---|
|**Cache Aside**|弱一致|好|低|✅ 最常用|
|Read/Write Through|中|中|高|框架场景|
|Write Behind|弱|极高|高|容忍丢失|
### 先删缓存 vs 先更库
方案A：先更库，再删缓存
```
// 写：更新数据库 → 删除缓存
// 读：缓存未命中 → 查库 → 回写缓存

// 问题：并发时可能把旧数据写回缓存！
// 场景：
// ① 线程 A 读：缓存未命中 → 查库（旧值 100）
// ② 线程 B 写：更新库（200）→ 删除缓存
// ③ 线程 A：回写缓存（100）← 旧值被写回！
// 结果：缓存是 100，库是 200 → 不一致（直到过期）
```
方案B：先删缓存，再更库
```
// 写：删除缓存 → 更新数据库
// 读：未命中 → 查库 → 回写缓存

// 问题：更新库期间，读请求会把旧值写回！
// 场景：
// ① 线程 A 写：删除缓存
// ② 线程 B 读：未命中 → 查库（旧值 100）→ 回写缓存 100
// ③ 线程 A：更新库（200）
// 结果：缓存 100，库 200 → 不一致！

// 比方案 A 风险更高（不一致窗口更长）
```
结论
```
// 两种都有问题，但方案 A（先更库再删缓存）更好：
// ① 不一致窗口更小
// ② 问题场景更少（B 的回写旧值概率更高）
// ③ 配合"延迟双删"解决

// 所以：推荐"先更新数据库，再删除缓存"
```
### 延迟双删
```
// 解决方案 A 的并发问题（回写旧值）
// 核心：删两次缓存，第二次延迟删
```
流程
```
// 写操作：
// ① 更新数据库
// ② 删除缓存（第一次删）
// ③ 延迟一段时间（如 500ms）
// ④ 再次删除缓存（第二次删）

// 原理：
// 延迟时间 > 读请求回写缓存的时间
// 第二次删掉刚回写的旧值 → 下一次读从库取新值

// 示例：
// ① 线程 A：更新库 200
// ② 线程 A：删缓存（第一次）
// ③ 线程 B：读 → 查库旧值 100 → 回写缓存 100
// ④ 线程 A：延迟 500ms 后 → 删缓存（第二次）→ 旧值被删！
// ⑤ 下次读：未命中 → 查库 200 → 回写 200 ✅
```
延迟双删的问题
```
// ① 延迟时间要合理（估不准可能失效）
// ② 第二次删除失败怎么办？（增加重试）
// ③ 延迟期间仍有不一致窗口

// 增强：
// ① 延迟双删 + 缓存过期时间兜底
// ② 第二次删除失败 → 消息队列重试
// ③ 用 binlog 订阅（Canal）删除缓存
```
### 最终一致性方案
方案一：Cache Aside+过期时间兜底
```
// ① 写：先更新库，再删缓存
// ② 缓存设过期时间（兜底）
// ③ 即使删缓存失败/回写旧值 → 过期后自然一致

// 简单可靠，最终一致
// 适合：大多数业务
```
方案二：binlog订阅（canal）
```
// ① 应用只更新数据库
// ② Canal 监听 binlog，发现数据变更
// ③ 主动删除/更新缓存

// 优点：
// ① 应用和缓存解耦（不用手动删）
// ② 不侵入业务代码
// ③ 可靠性高（binlog 有重放）

// 流程：
// 应用写库 → binlog → Canal → 删缓存
```
方案三：MQ异步删缓存
```
// ① 更新数据库
// ② 发送"删除缓存"消息到 MQ
// ③ 消费者删缓存
// ④ 失败重试（MQ 重试机制）

// 解决：删缓存失败的重试问题
```

|方案|实现成本|可靠性|实时性|
|---|---|---|---|
|延迟双删|低|中|中|
|过期兜底|最低|中|低|
|Canal binlog|中|高|高|
|MQ 异步删|中|高|高|
### 面试高频题
#### 题目1：缓存一致性怎么保证
```
// Cache Aside：先更库再删缓存 + 过期时间兜底
// 复杂场景：延迟双删、Canal、MQ
// 核心：最终一致（不是强一致）
```
#### 题目2：为什么删缓存而不是更新
```
// ① 更新缓存需要计算（复杂）
// ② 写多读少时更新浪费
// ③ 删除简单，下次读懒加载
// ④ 避免并发更新冲突
```
#### 题目3：先更库还是先删缓存
```
// 推荐先更库再删缓存
// 不一致窗口小
// 配合延迟双删解决回写旧值
```
#### 题目4：延迟双删是什么
```
// 更新库 → 删缓存 → 延迟 → 再删缓存
// 防止读请求回写旧值
```
#### 题目5：缓存和数据库可以强一致性吗
```
// 很难！
// 涉及分布式（缓存和库是两个系统）
// 一般用最终一致
// 强一致要加锁/事务，性能差
```
#### 题目6：有什么高级方案
```
// Canal 订阅 binlog 删缓存
// 本地消息表 + MQ
// 事务消息
// 读写锁（强一致但性能差）
```
