## 事务与隔离级别
事务是什么->ACID四大特性->三大读问题->四种隔离级别->隔离级别与MVCC关系->事务的使用->面试高频题
### 事务是什么？
Transaction：一组数据库操作，要么全部成功，要么全部失败。
```
-- 转账示例
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- 提交：两条都生效

-- 如果第二条失败：
ROLLBACK;  -- 回滚：两条都不生效
```
为什么需要事务？
```
// ① 保证数据一致性（转账不能只扣不加）
// ② 并发控制（多个用户同时操作）
// ③ 崩溃恢复（系统崩溃后数据不丢）
```
### ACID四大特性
Atomicity 原子性
```
// 事务是不可分割的最小单元
// 要么全部执行成功，要么全部回滚
// 实现：undo log（回滚日志）
// 记录修改前的旧值，回滚时反向操作恢复
```
Consistency 一致性
```
// 事务执行前后，数据总量保持一致
// 转账：A+B 的总金额不变
// 约束：外键、唯一约束、业务规则

// 一致性是"结果"，由原子性+隔离性+持久性共同保证
```
Isolation 隔离性
```
// 多个事务并发执行，互不干扰
// 实现：锁 + MVCC
// 隔离级别越低，并发越高，但问题越多
```
Durability 持久性
```
// 事务提交后，数据永久保存
// 即使系统崩溃也不丢失
// 实现：redo log（重做日志）
// WAL：先写日志，再写数据（崩溃时重放日志）
```

| 特性      | 含义         | 实现       |
| ------- | ---------- | -------- |
| **原子性** | 要么全成功要么全失败 | undo log |
| **一致性** | 数据前后一致     | 应用+约束    |
| **隔离性** | 并发互不干扰     | 锁 + MVCC |
| **持久性** | 提交后不丢失     | redo log |
### 三大读问题（并发异常）
Dirty Read 脏读
```
// 一个事务读到另一个事务"未提交"的数据

// 场景：
// 事务 A：UPDATE 余额 = 900（未提交）
// 事务 B：SELECT 余额 → 读到 900（脏数据！）
// 事务 A：ROLLBACK → 余额回到 1000
// 但 B 已经读到 900 了

// 危害：读到最终不存在的数据
```
Non-Repeatable Read 不可重复读
```
// 一个事务内，两次读同一行，结果不一样
// 因为其他事务"更新"了这行

// 场景：
// 事务 A：SELECT 余额 → 1000
// 事务 B：UPDATE 余额 = 900，COMMIT
// 事务 A：SELECT 余额 → 900（两次读不一致！）

// 危害：同一事务内数据不一致
// 本质：行被更新（UPDATE/DELETE）
```
Phantom Read 幻读
```
// 一个事务内，两次查询同一个范围，行数不一样
// 因为其他事务"插入"了新行

// 场景：
// 事务 A：SELECT * FROM t WHERE age > 20 → 3 行
// 事务 B：INSERT age=30，COMMIT
// 事务 A：SELECT * FROM t WHERE age > 20 → 4 行（多了一行！）
// 多出的行像"幻影"

// 本质：插入（INSERT）
```

|问题|读到什么|谁的提交状态|操作|
|---|---|---|---|
|**脏读**|未提交的数据|未提交|更新|
|**不可重复读**|同一行两次不一致|已提交|更新/删除|
|**幻读**|范围行数不一致|已提交|插入|
### 四种隔离级别
| 隔离级别                       | 脏读   | 不可重复读 | 幻读      | 并发度 |
| -------------------------- | ---- | ----- | ------- | --- |
| **READ UNCOMMITTED**（读未提交） | ❌ 可能 | ❌ 可能  | ❌ 可能    | 最高  |
| **READ COMMITTED**（读已提交）   | ✅ 解决 | ❌ 可能  | ❌ 可能    | 高   |
| **REPEATABLE READ**（可重复读）  | ✅ 解决 | ✅ 解决  | ⚠️ 基本解决 | 中   |
| **SERIALIZABLE**（串行化）      | ✅ 解决 | ✅ 解决  | ✅ 解决    | 最低  |
```
-- 查看/设置隔离级别
SELECT @@transaction_isolation;  -- MySQL 8.0
-- 默认：REPEATABLE-READ

SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```
READ UNCOMMITTED
```
// 最低级别：可以读到未提交的数据
// 三大问题都存在
// 几乎不用（除了极端的读场景）
```
READ COMMITED
```
// 只能读到已提交的数据
// 解决脏读，存在不可重复读和幻读
// Oracle 默认级别

// MySQL 实现：每次 SELECT 生成新的 ReadView
```
REPEATABLE READ
```
// 事务内两次读一致
// 解决脏读、不可重复读
// MySQL 默认级别！

// 为什么 MySQL 默认用这个？
// ① 靠 MVCC 实现快照读 → 幻读也基本解决
// ② 靠 Next-Key Lock 锁范围 → 当前读也不幻读
// 所以 MySQL 的 RR 实际解决了幻读（不像理论那样）

// 实现：事务第一次 SELECT 生成 ReadView，后续复用
```
SERIALIZABLE
```
// 最高级别：事务串行执行
// 所有读都加锁，性能最差
// 只有强一致场景才用（银行转账？）
```
### MySQL的RR是怎么解决幻读
两种读方式
```
// ① 快照读（Snapshot Read）
// 普通 SELECT（不加锁）
// 用 MVCC 读历史版本（ReadView）
// RR 下：同一事务复用同一个 ReadView → 读不到新插入的行
// → 快照读的幻读被 MVCC 解决 ✅

// ② 当前读（Current Read）
// SELECT ... FOR UPDATE / UPDATE / DELETE
// 读最新数据，加锁
// RR 下：用 Next-Key Lock（行锁 + 间隙锁）
// → 当前读的幻读被 Next-Key Lock 解决 ✅

// 结论：MySQL 的 RR 通过 MVCC + Next-Key Lock 基本杜绝了幻读，lock只是在需要时才加锁，如果加锁之前已经被其他事务修改，那么也会影响当前读，会出现幻读。
```
### 面试高频

> **Q:** "MySQL 默认隔离级别是什么？为什么？" 
> **A:** "MySQL 默认 REPEATABLE READ。虽然理论上 RR 存在幻读，但 MySQL 通过 MVCC（快照读）和 Next-Key Lock（当前读）实际解决了幻读，但如果一个事务里混着快照读和当前读，基于快照读的结果做业务决策然后写数据，可能会看到不一样的结果，所以严格来说不能完全解决。Oracle 默认 READ COMMITTED，因为它用别的方式解决一致性。"

> **Q:** "三种读问题的区别？" 
> **A:** "脏读：读到未提交的数据；不可重复读：同一行两次读不一致（更新）；幻读：范围查询行数变化（插入）。解决：读已提交解决脏读，可重复读解决不可重复读，串行化理论上解决幻读（MySQL 的 RR 也解决）。"
### 事务的使用
```
-- ① 显式事务
START TRANSACTION;      -- 或 BEGIN
UPDATE ...;
COMMIT;                 -- 提交
-- 或
ROLLBACK;               -- 回滚

-- ② 自动提交（默认开启）
-- 每一条 SQL 自动提交
SHOW VARIABLES LIKE 'autocommit';  -- ON
SET autocommit = 0;     -- 关闭

-- ③ 保存点（部分回滚）
START TRANSACTION;
UPDATE a SET ...;
SAVEPOINT sp1;          -- 保存点
UPDATE b SET ...;
ROLLBACK TO sp1;        -- 回滚到保存点，a 的修改保留
COMMIT;
```
事务的注意点
```
// ① 事务尽量短小（持有锁时间短）
// ② 不要在事务里做耗时操作（远程调用、大查询）
// ③ 大事务会占大量 undo log、锁资源
// ④ 避免长事务：连接池耗尽、锁冲突、回滚慢
```
