## 索引原理
索引是什么->为什么用B+树->聚簇vs二级索引->回表与索引覆盖->最左前缀->索引下推->索引失效场景->面试高频题
### 索引是什么
索引：帮助MySQL高效获取数据的数据结构。类似书的目录，避免全表扫描。
```
// 没有索引：全表扫描（一行行读，O(n)）
// 有索引：B+ 树查找（O(log n)）

// 100 万行数据：
// 全表扫描：读 100 万行
// B+ 树索引：约 3~4 层，读 3~4 个节点
```
索引的优缺点
```
// 优点：
// ① 查询快（减少 IO）
// ② 排序快（B+ 树有序）
// ③ 唯一性约束（唯一索引）

// 缺点：
// ① 占用磁盘空间
// ② 写操作变慢（要维护索引树）
// ③ 索引建多了反而拖慢插入/更新
```
### 为什么用B+树
对比选数据结构

|数据结构|查询|插入|问题|
|---|---|---|---|
|哈希表|O(1)|O(1)|不支持范围查询、排序|
|二叉搜索树|O(log n)|O(log n)|可能退化成链表 O(n)|
|AVL/红黑树|O(log n)|O(log n)|树太高，IO 次数多|
|**B+ 树**|O(log n)|O(log n)|✅ 适合磁盘场景|
为什么不用红黑树
```
// 红黑树是二叉树，每个节点只有 2 个子节点
// 100 万数据，树高约 20 层
// 每次查询要读 20 个节点 → 20 次磁盘 IO → 太慢！

// B+ 树是多叉树（MySQL 默认每个节点约 16KB）
// 每个节点可以存很多关键字（约 1000+ 个）
// 100 万数据，树高只有 3~4 层
// 查询只要 3~4 次磁盘 IO → 快！
```
为什么不用B树
```
// B 树：所有节点都存数据
// B+ 树：只有叶子节点存数据，非叶子只存索引

// B+ 树的优势：
// ① 非叶子节点更小 → 一个节点存更多索引 → 树更矮
// ② 叶子节点有链表 → 范围查询高效（直接遍历叶子）
// ③ 所有查询都到叶子 → 查询时间稳定
```
B+树结构
```
B+ 树（3 层）：
         [50 | 100 | 150]          ← 非叶子节点（只存索引）
        /      |       \
  [10|20|30] [60|80] [120|140|160] ← 非叶子节点
      ↓叶子     ↓叶子     ↓叶子
  [10→20→30] [60→80] [120→140→160] ← 叶子节点（存数据）
   ←──── 叶子节点双向链表 ────→（范围查询高效）
```
一个节点能存多少
```
// InnoDB 页大小默认 16KB
// 假设主键 bigint（8 字节）+ 指针（6 字节）≈ 14 字节
// 每个节点能存：16KB / 14 ≈ 1170 个索引

// 3 层 B+ 树能存：
// 1170 × 1170 × 16 = 约 2200 万行！    16是指一个索引页是6kb,如果行数据比较小是1kb,就可以有16条数据

// 所以：百万级数据只要 3 层，查询 3 次 IO
```
### 聚簇 vs 二级索引
聚簇索引（主键索引）
```
// 叶子节点直接存"完整数据行"
// 每张表只有一个（数据只能有一种物理排列）

// 特点：
// ① 查询主键：直接拿到数据（不用回表）
// ② 数据按主键物理排序

// InnoDB 自动创建聚簇索引：
// ① 有主键 → 用主键
// ② 没有主键 → 第一个唯一非空索引
// ③ 都没有 → 隐藏 rowid
```
二级索引（普通索引）
```
// 叶子节点存"主键值"（不是数据行）
// 一张表可以有多个

// 查询流程：
// ① 在二级索引 B+ 树找 → 拿到主键
// ② 用主键回聚簇索引找 → 拿到数据行
// ③ 这个过程叫"回表"

CREATE TABLE users (
    id INT PRIMARY KEY,       -- 聚簇索引
    name VARCHAR(50),
    age INT,
    INDEX idx_name (name)     -- 二级索引
);

-- 查询：
SELECT * FROM users WHERE name = '张三';
-- ① idx_name 找到 name='张三' → 拿到主键 id
-- ② 回表：用 id 去聚簇索引找 → 返回完整行
```
回表问题
```
// 回表 = 额外一次索引查找
// 二级索引查询如果返回大量行 → 大量回表 → 慢

// 解决：覆盖索引
```
### 覆盖索引
```
// 覆盖索引：查询的字段都在索引里 → 不用回表

-- 二级索引 idx_age (age, name)
CREATE INDEX idx_age_name ON users (age, name);

-- 查询：只需要 age 和 name
SELECT age, name FROM users WHERE age > 20;
-- 索引里就有这两个字段 → 不用回表 ✅ 快！

-- 查询：需要 id（主键）
SELECT id, age, name FROM users WHERE age > 20;
-- id 也在二级索引叶子（存的就是主键）→ 也不用回表 ✅

-- 查询：需要其他字段
SELECT age, name, email FROM users WHERE age > 20;
-- email 不在索引 → 必须回表 ❌ 慢
```
为什么覆盖索引快
```
// ① 减少回表（少一次 B+ 树查找）
// ② 二级索引比聚簇索引小（只存部分字段）→ IO 少

// 优化思路：
// "select 需要的字段尽量都放进联合索引"
// 但注意：索引不是越多越好（写开销）
```
### 最左前缀原则
联合索引
```
-- 联合索引 (a, b, c)
CREATE INDEX idx_a_b_c ON t (a, b, c);

// 能用到索引的查询：
WHERE a = 1                      ✅ 用到 a
WHERE a = 1 AND b = 2            ✅ 用到 a,b
WHERE a = 1 AND b = 2 AND c = 3  ✅ 用到 a,b,c

// 不能用到（或部分用）：
WHERE b = 2                      ❌ 没从 a 开始，用不到
WHERE c = 3                      ❌ 用不到
WHERE a = 1 AND c = 3            ⚠️ 只用 a，c 用不到（跳过 b）
WHERE b = 2 AND a = 1            ✅ 优化器会调整顺序（a,b）
```
为什么是最左前缀
```
// 联合索引的存储：先按 a 排序，a 相同按 b，b 相同按 c
// 所以只有从最左列开始，才能利用排序好的结构

// 类比字典：
// 索引 (姓, 名)：
// 查"姓=张" ✅ 能用（字典按姓开头）
// 查"名=伟" ❌ 不能用（不知道姓，无法定位）
```
范围查询的边界
```
-- 联合索引 (a, b, c)
WHERE a = 1 AND b > 2 AND c = 3
-- ✅ 用到 a（等值）
-- ✅ 用到 b（范围）
-- ❌ c 用不到！范围后面的列无法继续用索引

// 所以设计联合索引时：
// ① 等值条件的列放前面
// ② 范围条件的列放后面
// ③ 经常查询的列优先
```
### 索引下推（ICP）
索引下推是什么？
```
// ICP（Index Condition Pushdown，索引条件下推）
// MySQL 5.6+ 优化：把 where 条件下推到存储引擎层判断

// 联合索引 (name, age)
SELECT * FROM users WHERE name LIKE '张%' AND age > 20;
```
下推前后对比
```
// ❌ 没有 ICP（5.6 之前）：
// ① 用索引找到所有 name LIKE '张%' 的行
// ② 回表取出完整数据行
// ③ Server 层再判断 age > 20
// → 回表很多行

// ✅ 有 ICP：
// ① 用索引找到 name LIKE '张%' 的行
// ② 在索引里直接判断 age > 20（不下推则要回表判断）
// ③ 只对满足条件的回表
// → 回表少很多

// 效果：减少回表次数，尤其索引覆盖的列多时提升明显
```
### 索引失效场景
```
-- ① 左模糊查询
SELECT * FROM users WHERE name LIKE '%三';   -- ❌ 失效
SELECT * FROM users WHERE name LIKE '三%';   -- ✅ 有效

-- ② 对索引列做运算
SELECT * FROM users WHERE age + 1 > 20;      -- ❌ 失效
SELECT * FROM users WHERE age > 19;          -- ✅ 有效

-- ③ 对索引列用函数
SELECT * FROM users WHERE LOWER(name) = 'zhang';  -- ❌ 失效

-- ④ 隐式类型转换
SELECT * FROM users WHERE phone = 13800138000;  -- ❌ 失效
-- phone 是 varchar，和数字比较 → 转成数字 → 函数作用

-- ⑤ 隐式字符集转换（两个表 join 字符集不同）

-- ⑥ 违反最左前缀
CREATE INDEX idx_name_age ON users (name, age);
SELECT * FROM users WHERE age > 20;  -- ❌ 失效（没从 name 开始）

-- ⑦ 用 != 或 NOT IN
SELECT * FROM users WHERE age != 20;  -- ⚠️ 可能失效

-- ⑧ OR 连接非索引列
SELECT * FROM users WHERE age = 20 OR name = 'x';  -- ❌ 可能失效
-- OR 两边都要能走索引才行

-- ⑨ 索引列区分度低（如性别，全是 0/1）
-- 优化器可能放弃索引（全表扫更快）
```
### 面试高频

> **Q:** "索引失效有哪些场景？" 
> **A:** "① LIKE 左模糊；② 对列做运算或函数；③ 隐式类型转换；④ 违反最左前缀；⑤ OR 连接非索引列；⑥ 索引区分度低（优化器放弃）。核心：破坏了 B+ 树的有序性，或优化器认为全表扫更划算。"
### 面试高频题
#### 题目1：为什么MySQL用B+树不用红黑树
```
// 红黑树是二叉树，树高约 20 层 → 20 次磁盘 IO
// B+ 树多叉，树高 3~4 层 → 3~4 次磁盘 IO
// 磁盘 IO 是瓶颈，树越矮越快
```
#### 题目2：聚簇索引和二级索引
```
// 聚簇：叶子存数据行（主键索引），每表一个
// 二级：叶子存主键值，可多个，查询要回表
```
#### 题目3：什么是回表，怎么避免
```
// 二级索引查到主键，再去聚簇索引查数据 = 回表
// 避免：覆盖索引（查询字段都在索引里）
```
#### 题目4：最左前缀原则
```
// 联合索引 (a,b,c)，查询必须从 a 开始
// 等值列放前面，范围列放后面
```
#### 题目5：索引下推是什么
```
// 把 where 条件下推到引擎层，在索引里先过滤
// 减少回表次数（MySQL 5.6+ 默认开启）
```
#### 题目6：为什么不能建太多索引
```
// ① 占用磁盘空间
// ② 写操作要维护每棵 B+ 树（变慢）
// ③ 优化器选择困难
```
