## 日志系统
三大日志->redo log->binlog->undo log->WAL机制->两阶段提交->崩溃恢复->面试高频题
### 三大日志
| 日志           | 层次         | 内容             | 作用        |
| ------------ | ---------- | -------------- | --------- |
| **redo log** | InnoDB 引擎层 | 物理日志（页的修改）     | 崩溃恢复，不丢数据 |
| **binlog**   | Server 层   | 逻辑日志（SQL 语句/行） | 主从复制、归档恢复 |
| **undo log** | InnoDB 引擎层 | 逻辑日志（修改前的旧值）   | 回滚、MVCC   |
为什么需要三种
```
// redo log：保证"持久性"（崩溃后数据不丢）
// undo log：保证"原子性"（回滚）+ 支持 MVCC
// binlog：保证"主从复制"和"时间点恢复"
```
### redo log 重做日志
```
// 物理日志：记录"某个页做了什么修改"
// 如：把页 5 的偏移量 100 处改为 'A'
// 循环写入（环形结构），固定大小
```
WAL机制 Write-Ahead Logging
```
// 核心思想：先写日志，再写数据

// 为什么？
// ① 直接写磁盘（随机 IO）慢
// ② 先写 redo log（顺序 IO）快

// 流程：
// ① 修改 Buffer Pool 中的数据页（内存）
// ② 写 redo log（顺序写磁盘，快）
// ③ 返回成功
// ④ 之后（合适时机）把脏页刷到磁盘（异步）
```
为什么WAL快
```
// 磁盘顺序写 vs 随机写：
// 顺序写：磁头连续移动，快（几百 MB/s）
// 随机写：磁头来回跳，慢（几十 KB/s）

// redo log 是追加写（顺序）
// 数据页刷新是随机写
// 所以先记日志（顺序写）比直接写数据（随机写）快得多

// 参数：
// innodb_flush_log_at_trx_commit：
// 0：每秒刷盘（可能丢 1 秒数据）
// 1：每次提交刷盘（最安全，默认）✅
// 2：每次提交写 OS 缓存，每秒刷盘
```
环形结构
```
redo log（固定大小，循环写）：
┌──────────────────────────────────┐
│  [已写入] [正在写] [可覆盖] [已写入] │
└──────────────────────────────────┘
  write pos（写的位置）→ checkpoint（可覆盖的位置）

write pos 追上 checkpoint → 日志满了 → 强制刷脏页
```
### binlog 归档日志
```
// 逻辑日志：记录 SQL 或行变更
// Server 层，所有引擎通用
// 追加写，不覆盖（可归档）

// 三种格式：
// ① STATEMENT：记录 SQL（简单，可能不一致）
// ② ROW：记录行变更（准确，默认 5.7+）✅
// ③ MIXED：混合
```
作用
```
// ① 主从复制：从库读取 binlog 同步数据
// ② 数据恢复：基于 binlog 时间点恢复
// ③ 审计
```
刷盘时机
```
// sync_binlog：
// 0：由 OS 控制（可能丢）
// 1：每次提交刷盘（安全，但慢）✅
// N：每 N 次提交刷盘（折中）
```
### undo log 回滚日志
```
// 逻辑日志：记录修改前的旧值
// 每次修改前，把旧值写入 undo log

// 作用：
// ① 回滚：ROLLBACK 时反向操作恢复旧值
// ② MVCC：版本链
// ③ 崩溃恢复时回滚未提交事务
```
示例
```
-- 事务：把 name 从 'A' 改为 'B'
-- ① 写 undo log：记录旧值 'A'
-- ② 修改数据：name = 'B'
-- ③ 如果回滚：根据 undo log 恢复 name = 'A'

UPDATE users SET name = 'B' WHERE id = 1;
```
三种操作的回滚

|操作|undo log 记录|回滚动作|
|---|---|---|
|INSERT|记录新行的主键|DELETE 该行|
|DELETE|记录被删行的数据|重新 INSERT|
|UPDATE|记录修改前的旧值|改回旧值|
注意
```
// 大事务 → 大量 undo log → 占用空间
// 长事务 → undo log 不能清理 → 版本链变长 → 回滚/查询慢
// 所以：避免大事务、长事务
```
### 两阶段提交 2PC
redo 和 binlog的一致性
```
// 崩溃时可能出现：
// ① redo log 已写，binlog 没写
//    → 主库有这条修改，从库（binlog）没有 → 不一致！
// ② binlog 已写，redo 没写
//    → 主库恢复后没这条修改，从库却执行了 → 不一致！

// 解决：两阶段提交（保证 redo 和 binlog 一致）
```
两阶段提交流程
```
// 更新语句的完整流程：
// ① 修改 Buffer Pool 中的数据
// ② 写 undo log
// ③ 写 redo log（Prepare 阶段）← 第一阶段
// ④ 写 binlog
// ⑤ 提交事务：redo log（Commit 阶段）← 第二阶段
// ⑥ 返回成功
```
崩溃恢复怎么判断
```
// 崩溃恢复时，检查 redo log 的状态：
// ① 只有 Prepare，没有 Commit：
//    → 检查 binlog 是否完整
//    → binlog 完整 → 提交（保持一致）
//    → binlog 不完整 → 回滚（保持一致）

// ② Prepare + Commit 都有：
//    → 事务已提交，重放即可

// 效果：redo 和 binlog 要么都有，要么都没有
// → 主从数据一致
```
崩溃恢复流程
```
崩溃恢复：
    ↓
① 从 redo log 找出所有未提交的事务
    ↓
② 逐个检查：
   - redo 有 Prepare + binlog 完整 → 提交该事务
   - redo 有 Prepare + binlog 不完整 → 回滚该事务
   - redo 只有 Prepare 无 binlog → 回滚该事务
    ↓
③ 结果：redo 和 binlog 数据一致
```
### 面试高频题
#### 题目1：redo log 和binlog的区别
```
// ① 层次：redo 在引擎层，binlog 在 Server 层
// ② 内容：redo 物理日志，binlog 逻辑日志
// ③ 写入：redo 循环写，binlog 追加写
// ④ 作用：redo 崩溃恢复，binlog 主从复制/归档
// ⑤ 引擎：redo 只有 InnoDB，binlog 所有引擎
```
#### 题目2：什么WAL，为什么快
```
// Write-Ahead Logging：先写日志再写数据
// 日志顺序写（快），数据随机写（慢）
// 先记日志保证不丢，数据异步刷盘
```
#### 题目3：为什么需要两阶段提交
```
// 保证 redo 和 binlog 一致
// 防止崩溃时主库和从库数据不一致
```
#### 题目4：三种日志各干什么
```
// redo：持久性（崩溃恢复）
// undo：原子性（回滚）+ MVCC
// binlog：复制 + 归档
```
#### 题目5：undo log能清理吗
```
// 事务提交后，undo log 的"回滚"功能不再需要
// 但 MVCC 还需要（可能有人还在读旧版本）
// 当所有 ReadView 都不需要时，purge 线程清理
```
